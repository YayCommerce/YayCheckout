# Architecture

**Purpose:** how YayCheckout's parts fit together: boot, the admin-shell sync, the server layers and who writes what, how a layout is stored and picked, the storefront, preview links, blocks and the embedded editor, the Free/Pro split, how the admin SPA reaches WordPress, the compatibility scan, release, and tests. Each claim names the file that decides it; read that file for the details.

**Update when:** a change moves a boundary described here: boot order or autoloading, the admin-shell sync, a layer or a writer, a stored option or post field, how the storefront picks or renders a layout, the preview rules, how blocks register or which editor offers them, the Free/Pro seam or its checks, how the SPA loads or calls WordPress, the compatibility scan, the release steps, or the test harness. A feature that stays inside an existing layer needs no update.

Commands and hard rules live in [CLAUDE.md](../CLAUDE.md). Citations give a path and a symbol, not a line number: search for the symbol. Where the code has a known gap, this doc states the behaviour as it is today.

## Boot and autoload

- `yaycheckout.php` is the entry point. Each of its constants is defined only when not already defined, so `wp-config.php` can override any of them. `YAYCHECKOUT_IS_DEVELOPMENT` is the one a site sets (see [SPA and WordPress](#spa-and-wordpress)).
- Two autoloaders run. `composer.json` classmaps only the scoped admin-shell in `vendor-prefixed/src/` and `YayCheckoutPluginAdapter.php`; `yaycheckout.php` requires `vendor/autoload.php` unconditionally, then the adapter file directly. Product classes in the `YayCheckout\` namespace go through the loader in `yaycheckout.php`, which maps them onto `includes/`, requires a file only if it exists, and uses `require_once` because a doubled backslash in a class name maps to the same file. `boot_pro()` requires `ProServiceProvider.php` by path, and Composer's `autoload-dev` maps `YayCheckout\Tests\` to `tests/`.
- That `file_exists` check lets one tree run with parts missing: Free has no `includes/Pro/`, and release zips have no `RegisterDev.php`, so code checks for those classes first (`is_readable` in `YayCheckout::boot_pro()`, `class_exists` in `RegisterFacade`) and names them only behind that check.
- Boot runs on `plugins_loaded`:
  - priority 5: admin-shell boots and registers the adapter (see [the next section](#admin-shell-sync-and-scoping));
  - priority 10: `plugin_init()` shows a notice and stops if WooCommerce is missing. Otherwise it declares HPOS compatibility (`Engine\ActDeact::before_woocommerce_init`), builds the `YayCheckout` singleton and loads translations.
- `includes/YayCheckout.php` wires everything by hand in its constructor, with no container. `boot_pro()` runs first so `Support\Plan::is_pro()` is settled before any component reads it; then REST, asset registration, the admin page, blocks, the post type, the layout guards, the editor embed, and the storefront renderers.
- Activation stores nothing: settings and each layout's design derive from their schemas on read. `uninstall.php` deletes layouts and options named `yaycheckout_*` only when the merchant turned on `general.delete_data_on_uninstall`; the catalogue transient, extra-field order meta and the other sites of a network stay behind. It runs without the autoloader, so it repeats those keys as literals.

## Admin-shell sync and scoping

- Admin-shell is a private Composer package shared by the YayCommerce plugins. It draws the shared YayCommerce admin menu and its common pages, and adds this plugin's submenu entry.
- Every plugin ships its own copy, so php-scoper rewrites the package into `vendor-prefixed/` under the `YayCheckoutScoped` namespace (`scoper.inc.php`). [The decision record](decisions/2026-10-05-admin-shell-scoped-with-php-scoper.md) says why. With several YayCommerce plugins active, the newest copy draws the shared menu.
- `YayCheckoutPluginAdapter.php` joins the two. It is a global class that implements the scoped menu-adapter interface and stays out of scoping. It names the page slug `yaycheckout` and the capability `manage_woocommerce`, and its page callback prints the SPA's mount point, `<div id="yaycheckout">`.
- The sync lives in the package's own scripts. `./scripts/run.sh dev` runs a full `composer update`, then `vendor/bin/yaycommerce-update`, which deletes `vendor-prefixed/`, updates admin-shell, requires php-scoper and thecodingmachine/safe as dev dependencies (which can rewrite `composer.json`), regenerates `scoper.inc.php` from the package's template keeping only the prefix and the adapter's name, then scopes the package and dumps the classmap.
- `./scripts/run.sh release` runs the `yaycommerce-prerelease` variant, which ends with `composer install --no-dev`. A plain `composer install` never builds `vendor-prefixed/`.

## Server layers and write ownership

- REST lives under `BaseRestController::REST_NAMESPACE` (yaycheckout/v1). `Engine\RestAPI` builds the Free controllers on `rest_api_init`; `Pro\ProServiceProvider::rest_endpoints()` builds the Pro ones, so the Free build simply has no such route. Every route, ours and core's, requires `LayoutPostType::CAPABILITY` (`manage_woocommerce`).
- Callbacks run through `BaseRestController`: `exec_read`, `exec_write_wp` for WordPress API writes, and `exec_write`, which wraps a SQL transaction, for custom tables. There are no custom tables, so nothing uses `exec_write`. WordPress writes go through the object cache, and a `ROLLBACK` would leave a persistent cache holding rolled-back data; ordering the writes so a partial failure leaves a safe state is the substitute. `LayoutRepository::archive()` deactivates before it trashes, so a refused trash leaves the layout deactivated but not archived. A thrown exception becomes a 500, its message goes back to the client, and `Helpers\Logger::exception()` logs it.
- The layers under `includes/`:
  - `Models/` are values that own their schemas and the storage keys of what they describe, and validate input against those schemas;
  - `Repositories/` hold every option call, most post and meta calls, and the invariants of their own writes;
  - `Services/` compute on data a caller already fetched, with no storage calls (`LayoutMarkupReader`, `LayoutAssignment`, `RequiredFieldOverlay`, `RequiredIndicator`, `ExtraFieldSubmission`);
  - `Controllers/` are thin, apart from `LayoutCoreRestController`, which gates core's layout routes, and `LayoutTemplateCatalogue`, which isn't a controller but the template list and its plan rule;
  - `Renderer/` hooks the storefront;
  - `Engine/` holds activation, REST and asset wiring, the admin page, the editor embed and the layout guards, which enforce the repositories' rules on core's paths with their own post and meta calls.
- Writers: `LayoutRepository` writes layouts (with their `Layout::META_TEMPLATE`) and the active set; `SettingsRepository` writes `yaycheckout_settings` and its flags (`yaycheckout_settings_updated_at`, `yaycheckout_reviewed`, `yaycheckout_setup_done`); core's REST API (wp/v2) writes `post_content` and the layout's design (`Layout::META_DESIGN`) from the editor; `CompatibilityCatalogueRepository` caches the catalogue in a transient; `Renderer\CheckoutExtraFields` writes extra-field order meta when the order is created, and remembered extra-field values to the WooCommerce session (`CheckoutExtraFields::SESSION_VALUES`) until then; `Engine\LayoutTrashSync` deletes core's trash timestamp; `Renderer\PreviewRequest` puts a preview's sample products in the viewer's cart; `Renderer\CartItemQuantity` changes cart item quantities and removes items from the shopper's cart through its wc-ajax action; `FontRepository` uploads a layout's design font into core's Font Library (`wp_font_family` and `wp_font_face` posts, files in `wp_get_font_dir()`), called by `Engine\DesignFontInstall` when a design is saved (the design meta written by any writer, and every editor Save) ([why](decisions/2026-10-11-picked-fonts-installed-into-font-library.md)).
- `Models\Settings::schema()` describes every setting and `Models\LayoutDesign::schema()` every design token, each with its type and default. `Settings::from_option()` and `LayoutDesign::from_meta()` project what is stored through the schema, so a missing, stale or invalid value reads as its default and neither the SPA nor the editor meets an unknown shape; `Settings::sanitize()` checks a settings write against the same schema, and `LayoutDesign::rest_schema()` a design write.
- `POST /setup` (`Controllers\SetupRestController::complete_setup()`) validates the template before its first write, then creates the draft from it and marks setup done. Once setup is done it answers 409, so a later retry can't add a second draft; two overlapping requests both pass the check. A re-run from Settings sends `rerun`, which skips that check and always adds a draft. `LayoutTemplateCatalogue::assert_available()` decides which templates a plan may pick, and the draft is built from the picked one. `POST /mark-setup-done`, the wizard's Skip, sets the flag without a layout.

## Layouts: one post, a status and an active set

- A layout is one `yay_checkout_layout` post (`PostTypes\LayoutPostType`): `post_content` holds the block markup, and `post_status` says whether shoppers may see it. Its design is the `Layout::META_DESIGN` meta (`Models\LayoutDesign`), the only design there is: every section of `LayoutDesign::schema()` (colours, typography, inputs) with every token, plus custom CSS. Any token may be empty (`''`, or `null` for a size or radius), and an empty token prints nothing, so the theme shows through. A colour is a hex colour or a theme preset's `var(--wp--preset--color--<slug>)`, and the background (a `fill`) may also be a gradient, written out to `LayoutDesign::GRADIENT_PATTERN` or a `var(--wp--preset--gradient--<slug>)`. The patterns refuse anything that could end a declaration, since tokens print unescaped, and the storefront and the editor canvas both define the preset properties. It is registered in REST with a schema built from `LayoutDesign::schema()`, so core refuses an invalid token. `LayoutRepository::duplicate()` copies it with the rules, and Pro's export file carries it; import (`LayoutImportReview::from_envelope()`) projects it through `LayoutDesign::from_meta()` instead of refusing the file, so a missing or malformed section imports as empty. [The decision record](decisions/2026-10-05-layout-is-one-post.md) says why. Publishing is a status change, the same one `activate()` and cron's `publish_future_post` make; the wire `status` is `post_status` (`Enums\LayoutStatus`). Merchants never see it: the SPA, the editor and the preview banner show Active (in the active set), Inactive or Archived ([decision record](decisions/2026-10-08-deactivate-unpublishes.md)).
- A new layout, and the setup wizard's, starts from a template in `LayoutTemplateCatalogue`: `templates/layouts/<slug>/markup.php` gives its blocks, `design.json` its `Layout::META_DESIGN` with every section set, and `Layout::META_TEMPLATE` (`_yaycheckout_template`) records the slug. A template missing either file is listed as Coming soon (`available: false`) and refused. Blank is `LayoutTemplateCatalogue::DEFAULT_SLUG`, Classic two-column. Duplicate copies the slug and import leaves it unset. Reset (`LayoutRepository::reset()`) puts back the markup and design of the layout's template, or of the default when it has none still available, without the plan lock; the old markup stays as a revision, but the design meta has none. Classic two-column is a white header bar (logo or site title, a Cart › Checkout › Order received breadcrumb, "Secure checkout") over a constrained Group (1120px) holding the Checkout block with a two-column Columns: the form left (Express Pay, a contact row with Login, Email, Billing, Shipping, Shipping methods, Payment, Order Note, then the terms sentence, Place Order and Return to cart), and right a sticky Group holding a white card with Order Summary (Items, Coupon Form, Totals, with room for the merchant's blocks around them) and the privacy and terms links. It has no footer, and the terms sentence and links print only for the pages that exist. Its look comes from block settings, not plugin CSS: the summary sticks only where the theme's settings enable sticky positioning, and on phones the columns stack form first. Its logo, links and labels are fixed at creation.
- The post type maps every capability to `manage_woocommerce` with `map_meta_cap => false`. `Controllers\LayoutCoreRestController` is its `rest_controller_class`: it requires the capability for reads too, because core answers a logged-out read of a published post, and its `prepare_item_for_database()` refuses a wp/v2 save that would leave a layout published or scheduled while `LayoutMarkupReader::publish_error()` objects. wp-admin's Quick Edit and Bulk Edit don't pass through it, so they can publish such a layout.
- `LayoutRepository::publish()` and `activate()` also refuse on `publish_error()`, and refuse an archived layout, since setting its status would restore it from the trash. `publish()` goes through `wp_publish_post()`, so a scheduled or pending layout goes live at once; `activate()` publishes first unless the layout already is, and checks the rules either way. `deactivate()` drops the layout from the active set and moves a published, pending or scheduled layout to draft; Free's `set_active()` deactivates the layout it replaces the same way. Layouts published but inactive from before this rule stay published and show as Inactive.
- The active set is the `Layout::OPTION_ACTIVE` option, an ordered list of ids, and shoppers see only layouts in it. `LayoutRepository::active()` doesn't re-check `post_status`: it relies on `LayoutActiveGuard` (below) to drop a layout that stops being visible, and an active layout that becomes scheduled keeps serving its current content. Free keeps one (`set_active()` replaces it, and `active_ids()` reads only the last id stored); Pro keeps several, most recently activated last.
- Guards keep the set honest (`includes/Engine/`):
  - `LayoutActiveGuard` refuses to trash or delete an active layout, and drops one whose status moves to anything but published or scheduled (draft, pending or private). It and `LayoutTrashSync` call `LayoutRepository::forget_active()`, which leaves the status alone, because `deactivate()` would change it again inside the transition;
  - `LayoutTrashSync` removes WordPress's trash timestamp, so an archived layout is never purged by cron;
  - `LayoutCapGuard` enforces the Free limit (`LayoutRepository::FREE_LIMIT`) on core's wp/v2 insert, because any shop manager can POST there directly. It misses a layout started from wp-admin's `post-new.php`, which core inserts as an auto-draft and the editor then saves as an update, and `LayoutRepository::count()` leaves private layouts out.
- `LayoutRepository::archive()` deactivates before it trashes. With `EMPTY_TRASH_DAYS` set to 0, core's `wp_trash_post()` deletes instead, so archiving deletes the layout. `restore()` doesn't check the limit. `delete()` refuses a layout that isn't archived; core's wp/v2 `DELETE ?force=true` doesn't check.
- Layout lists are paged server-side (`Models\LayoutQuery::PER_PAGE`), and search matches titles only (`LayoutRepository::match_search_to_title()`), since `post_content` is markup. The lists show only listed statuses and the archive, so a private layout appears in neither.

## Storefront

- `Renderer\CheckoutPage` takes over the checkout page on `wp` when a layout resolves and, with safe mode on (`general.safe_mode`, default on), `Renderer\CheckoutHealth::problem()` finds nothing and the layout has no recorded render failure. The order-received and order-pay endpoints stay WooCommerce's (`CheckoutPage::on_checkout_page()`). Otherwise WooCommerce is untouched, except that the opt-in `advanced.force_enqueue_checkout_scripts` setting (`Renderer\CheckoutScripts`) still loads WooCommerce's checkout scripts. A preview link resolves its own layout first (see [Preview links](#preview-links)).
- **Admin bar:** on a page `CheckoutPage::takes_over()`, `Renderer\CheckoutAdminBar` removes core's Edit Page and Edit site items, which edit neither the page nor the template shown, and gives users with `LayoutPostType::CAPABILITY` an Edit Layout item that opens the rendered layout (the previewed one on a preview link) in the SPA's editor (`Helpers\AdminUrlHelper::edit_layout()`).
- **Which layout:** `LayoutRepository::active()` gets the shopper facts that `CheckoutPage` reads (roles, logged in, `wp_is_mobile()`). Free serves its one active layout and ignores its rules; Pro hands the set to `Services\LayoutAssignment::pick()`, most recently activated first, which serves the first layout whose rules match (groups ORed, conditions ANDed; no rules matches everyone). No match leaves WooCommerce's checkout.
- Every request picks afresh, AJAX and the order submit included, with no pin, and nothing in the checkout POST says which layout rendered the form. Each `Enums\ConditionType` reads a fact that holds for the life of a form, so the shopper can't swap the layout mid-form; a fact the shopper can change, such as billing country or cart, must never become a condition. A merchant's change between render and submit (activating, editing the markup or rules, safe mode) still changes the layout the order is validated against.
- **Safe mode:** `CheckoutHealth` owns every rule that makes a layout unsafe to serve: the layout's `LayoutMarkupReader::publish_error()`, then store-level ones (an active plugin the catalogue marks `conflict` below its `fixed_in`; no enabled classic gateway usable in the layout while the native checkout has one), then the `yaycheckout_safe_mode_problem` filter. Each reads store configuration only, never the cart, so the render, AJAX and submit requests of one form agree; the storefront reads the catalogue through `CompatibilityCatalogueRepository::cached()`, which never fetches. A render failure (a `\Throwable` on the page or in an `update_order_review` fragment (`CheckoutFragments::fragments()`), output without `id="place_order"`, or the request ending mid-render by a fatal, `exit` or `wp_die()`, caught by `CheckoutPage::record_fatal()`) is only visible to the render request, so `CheckoutPage::page_template()` records it in `CheckoutPage::OPTION_RENDER_FAILURE` (`yaycheckout_render_failure`: layout id, md5 of `post_content`, reason cut to `CheckoutPage::REASON_MAX_LENGTH` characters, time) and, with safe mode on, discards its output and returns the theme's template in the same request (a failing fragment returns WooCommerce's own fragments instead). The record is a circuit breaker: `CheckoutPage::render_failure( $layout )` returns its reason while the layout's id and content hash match it, `CheckoutHealth::problem()` checks it before the markup and store rules, and a content save resets it. With safe mode off, a throw propagates as before and the layout renders whatever its problem. A preview renders regardless and never records. `CheckoutHealth::reported_problem()` feeds the Compatibility page and `Engine\Admin\SafeModeNotice`.
- **Rendering:** `template_include` at `PHP_INT_MAX` renders the layout in `CheckoutPage::render()`, then swaps in `templates/checkout-page.php`, which prints it (`CheckoutPage::html()`); it is rendered before `wp_head()` (block themes print the import map there), inside the template's own document, on every theme: no theme header or footer, while `wp_head()` still loads the theme's styles. No page title is printed. `CheckoutPage` dequeues WooCommerce's `woocommerce-general`, `woocommerce-blocktheme`, `woocommerce-layout` and `woocommerce-smallscreen` and loads `Renderer\CheckoutBaseStyles`: `assets/css/checkout-base.css`, the design font's `@font-face` rules (`Renderer\DesignFonts`, from its Font Library install; none when the theme loads the font itself), then the design. The base removes the theme's horizontal margin, padding and max-width around the layout and resets the theme.json content size, wide size and root padding inside it, so only the layout's own blocks limit its width; it also styles what several blocks or WooCommerce itself print (field rows, inputs, select2, checkboxes, notices, the blockUI spinner, buttons, the Order Summary tables). Markup one block alone prints is styled in that block's `style.css`; Payment and Shipping methods each draw their own rows, with no shared partial. The `checkout` block prints WooCommerce's `<form name="checkout">`, and every section block sits directly inside it; nothing stops the Checkout block itself being nested. `Renderer\DesignStyles` prints the rendered layout's design (`Models\LayoutDesign`) as `--yaycheckout-*` custom properties, one for each token that isn't empty, then a page rule for the page's background, text colour and font, with a font a heading rule that makes the checkout's headings inherit it (a gradient background prints as `--yaycheckout-background-gradient` and the page's `background-image`, never as `--yaycheckout-color-background`, so inputs and rows keep their solid fallback), then the site-wide custom CSS (the setting `advanced.custom_css`, Settings → Advanced) and the layout's, each checked on print so a rejected one drops only itself. Tokens are values, never selectors: the base and block CSS read each property with a neutral fallback that follows the theme, so an empty token prints nothing. `LayoutEditorCanvas` loads the same base and the edited layout's tokens into the editor canvas, without either custom CSS.
- **Fields:** the Field and Email blocks call `woocommerce_form_field()` with the value classic checkout prints, `WC()->checkout()->get_value()` (the session, or the account when logged in), so a reload keeps what the shopper typed. `Renderer\CheckoutFieldDefaults` also gives each billing or shipping row WooCommerce's `address-field` and `update_totals_on_change` classes from `woocommerce_checkout_fields`, which `checkout.js` needs to send typed address changes to `update_order_review`; layout classes such as `form-row-first` are left out. A collapsed field that holds a value prints open. Which address is the main one follows WooCommerce's `woocommerce_ship_to_destination` (`Renderer\CheckoutDifferentAddress::destination()`). When billing is main, the Different address block prints WooCommerce's own `ship_to_different_address` checkbox, and the Shipping block's `shipping_address` class lets `checkout.js` show it and send its rates fields while the box is ticked. When shipping is main, the Shipping block prints WooCommerce's box checked and hidden, and the Different address block prints "Use same address for billing" (`yaycheckout_same_billing`): `assets/js/checkout-different-address.js` hides Billing and mirrors Shipping into it, and `CheckoutDifferentAddress` copies the posted shipping address into billing and makes billing's address fields optional for that request. A layout with no Different address block always saves Shipping as typed; one with no Billing section, when shipping is main, always copies it into billing. With `billing_only`, or a cart that needs no shipping address, neither block prints and WooCommerce copies billing into shipping. Of WooCommerce's form hooks, only those around the payment methods and Place order fire; `woocommerce_before_checkout_form`, the customer-details pair, `woocommerce_checkout_billing` and `woocommerce_checkout_shipping` (account fields, order notes) never do. The Create account block prints the account part of form-billing.php when WooCommerce allows registration at checkout and the visitor is a guest: the `createaccount` checkbox while guest checkout is on, then `get_checkout_fields( 'account' )` through `woocommerce_form_field()`, between `woocommerce_before_checkout_registration_form` and `woocommerce_after_checkout_registration_form`. `WC_Checkout::process_customer()` creates the account, and WooCommerce's `checkout.js` toggles the fields. A layout without the block still has WooCommerce require the account fields when guest checkout is off. The Order note block prints `order_comments` through `woocommerce_form_field()`, with Field's Show field and Required settings; `RequiredFieldOverlay::apply_order_note()`, run by `CheckoutRequiredFields`, makes WooCommerce require the note exactly when the block does, and WooCommerce saves it as the order's customer note. The Additional fields block prints the `woocommerce-additional-fields` part of form-shipping.php without its heading: `get_checkout_fields( 'order' )` between `woocommerce_before_order_notes` and `woocommerce_after_order_notes`, while `woocommerce_enable_order_notes_field` allows it. It leaves out `order_comments` when the layout has an Order note block.
- **Login:** The `yaycheckout/login` block (`Renderer\CheckoutLogin`) prints a sentence only when `woocommerce_enable_checkout_login_reminder` is `yes` and the shopper is logged out. The editor reads that option from `window.yayCheckoutLogin`. The merchant selects which phrase is the control (a span with `CheckoutLogin::TRIGGER_CLASS` in `text`, read by `CheckoutLogin::trigger_parts()`) and whether it links to `wp_login_url( checkout )` or opens a modal; a block that still has plain `text` and `linkText` uses `CheckoutLogin::split_link()`. The modal's form lives in a `<template>` and is moved to `document.body`, so it is not nested in `<form name="checkout">`. `wc_ajax_yaycheckout_login` calls `wp_signon()`; the next request, `wc_ajax_yaycheckout_login_state`, returns the logged-in layout id, account values for empty fields, and fresh `update-order-review` and `woocommerce-process_checkout` nonces. The form keeps its node: the script fills empty fields, removes the reminder, and fires `update_checkout`. It reloads the page when `form.checkout` is missing (guest checkout and registration both off: the reminder prints above "You must be logged in to checkout.") or when `data-yaycheckout-layout` differs from the logged-in layout id. New layouts do not include the block; the merchant adds it.
- **Validation:** `Renderer\CheckoutRequiredFields` filters `woocommerce_checkout_fields` at 9999 through `Services\RequiredFieldOverlay::apply()`, so a billing or shipping field is required exactly when its block says so, over WooCommerce's country rules too, and any email field always is; billing and shipping fields the layout leaves out become optional. The filter isn't gated on the checkout page, because the checkout POST validates before `is_page()` works, so it applies to any classic checkout form on the site. `assets/js/checkout-field-requirements.js` re-applies flags and labels after WooCommerce's `address-i18n.js` resets them on a country change.
- **Remember value:** an Extra field block with `rememberValue` on carries `data-yaycheckout-remember`. On a change in one, `extra-field/view.ts` posts the checkout form to `wc_ajax_yaycheckout_remember_extra_fields`, guarded by WooCommerce's `update-order-review` nonce from `wc_checkout_params`. `CheckoutExtraFields::remember()` cleans the remembered Keys with `ExtraFieldSubmission::collect()` and replaces `SESSION_VALUES`; It also answers `woocommerce_checkout_get_value` for remembered Keys (`''` when nothing is stored, so customer meta under the same Key never leaks in), so `render.php` reads them through `CheckoutFieldDefaults::value()` like the Field block, and `RevealLink::collapsed()` prints a field holding a value open. `persist()` clears them once the order is created. Off by default, so existing layouts keep their behaviour until the merchant turns it on.
- **Coupon form:** the `coupon-form` block has no `parent`, so it can sit inside the checkout form or beside it, and it prints no `<form>` of its own because forms can't nest. WooCommerce's `checkout.js` applies a coupon only on a `form.checkout_coupon` submit, so `assets/js/checkout-coupon-form.js` posts to WooCommerce's `apply_coupon` endpoint itself, prints the notice under the field and fires `update_checkout`. The field carries no `input-text` or `form-row` class, so WooCommerce's inline validation leaves it alone, and the script catches Enter, which would otherwise submit the checkout. The script is registered as `BlockRegistry::COUPON_FORM_SCRIPT` and named by the block's `viewScript`, so core loads it only where the block renders; a handle, not `file:`, because the blocks build can't declare the `wc-checkout` dependency that supplies `wc_checkout_params`. Like WooCommerce's own coupon form, the block renders nothing when coupons are off or a guest must log in first.
- **Extra fields and fragments:** `Renderer\CheckoutExtraFields` reads the served layout's extra fields (`LayoutMarkupReader::extra_fields()`), checks them with `Services\ExtraFieldSubmission::collect()` and stores them as order meta on `woocommerce_checkout_create_order`; like the overlay, it runs on any classic checkout. A Key must match `LayoutMarkupReader::EXTRA_FIELD_KEY_PATTERN`, because a leading underscore reaches WooCommerce's internal order setters. `Renderer\CheckoutFragments` swaps the shipping-rate and payment fragments only for sections `LayoutMarkupReader::slots()` finds in the layout; a Slot block's name counts as a section. Order Summary's Items and Totals blocks are found by block name instead (`CheckoutFragments::BLOCK_FRAGMENTS`), so a Slot can't trigger them. When the layout has either, `update_order_review` swaps WooCommerce's `checkout/review-order.php` for the empty `templates/review-order-skipped.php`, so the table WooCommerce would build and the layout would discard never runs, and its review-order hooks fire once. Totals leaves out the shipping rates, which the Shipping Methods block offers (the default layout includes one); Total still counts them, and a layout without that block shows no rate choice. Shipping Methods prints its own rate list from `WC()->shipping()->get_packages()`, not WooCommerce's `shop_table` or `wc_cart_totals_shipping_html()`: each rate keeps WooCommerce's `shipping_method` input and runs `woocommerce_after_shipping_rate`, and the review-order shipping hooks wrap any plugin `<tr>` output in a table beside the list. `woocommerce_cart_shipping_method_full_label` receives only the method name; the price is a separate element with the same tax and zero-cost rules as `wc_cart_totals_shipping_method_label()`. Each review-order hook fires in the block that prints its content: the cart-contents hooks in Items, the order-total hooks in Totals, the shipping hooks in Shipping Methods and the payment hooks in Payment. When the Place Order block shows the order total, it also sends `#place_order`: `render.php` prints only the bare button during AJAX (without `woocommerce_order_button_html`, whose extra siblings would repeat), and `checkout.js` swaps it so `data-total` follows the cart.
- **Hide when empty:** a core Group, Columns or Column (`HideWhenEmpty::CONTAINERS`) can watch YayCheckout blocks inside it (`yaycheckoutHideWhenEmpty`, a list of `blockId`s) and hides while every one of them is empty. Only blocks whose `block.json` sets the `yaycheckoutWatchable` support can be watched: Shipping methods (empty when the cart needs no shipping), Payment (when the order needs no payment), Express pay (when `wc_get_pay_buttons()` prints nothing), Slot (when nothing hooked into it prints anything), Field (while WooCommerce's country locale hides it, read by `CheckoutFieldDefaults::hidden_for_country()`), and Coupon form, Login and Create account (when they print nothing). Each prints `data-yaycheckout-block-id` and, when empty, `data-yaycheckout-empty` on its wrapper through `HideWhenEmpty::wrapper()`; a missing wrapper counts as empty. `Renderer\HideWhenEmpty` filters `render_block_{name}` for each container: it ignores ids no watchable descendant carries, adds `data-yaycheckout-hide-when-empty` and, when `HideWhenEmpty::hidden()` says so, `yaycheckout-hidden-when-empty`, and enqueues `assets/js/checkout-hide-when-empty.js`. The shipping-rate and payment fragments carry `data-yaycheckout-live` and their own empty marker, so after `updated_checkout` the script copies it to the block wrapper and re-applies the rule, which it mirrors from `hidden()`; PHP owns what empty means. A Field's wrapper carries `data-yaycheckout-locale`: on `country_to_state_changing`, after `address-i18n.js` (a dependency) has shown or hidden the row for the new country, the script marks the Field empty while its row is hidden. Coupon form, Login, Create account, Slot and Express pay keep their first-paint marker. A hidden container's required fields still validate. The editor's panel (`packages/blocks/src/shared/hide-when-empty.tsx`, layout editor only) lists each Slot by name and each Field by label and key, warns about them (a watched Field excepted, since it hides only when its own country does), and gives a copied block a new `blockId`.
- **Coupon form:** the `coupon-form` block has no `parent`, so it can sit inside the checkout form or beside it, and it prints no `<form>` of its own because forms can't nest. WooCommerce's `checkout.js` applies a coupon only on a `form.checkout_coupon` submit, so `assets/js/checkout-coupon-form.js` posts to WooCommerce's `apply_coupon` endpoint itself, prints the notice under the field and fires `update_checkout`. The field carries no `input-text` or `form-row` class, so WooCommerce's inline validation leaves it alone, and the script catches Enter, which would otherwise submit the checkout. The script is registered as `BlockRegistry::COUPON_FORM_SCRIPT` and named by the block's `viewScript`, so core loads it only where the block renders; a handle, not `file:`, because the blocks build can't declare the `wc-checkout` dependency that supplies `wc_checkout_params`. Like WooCommerce's own coupon form, the block renders nothing when coupons are off or a guest must log in first. The Apply button is the `coupon-button` child block, which the form's template locks in, so its style supports (colour, typography, border, spacing, Fill or Outline) land on the `<button>`; the script still finds it by `.yaycheckout-coupon-form__apply`. The form's Button colors reach it as `--yaycheckout-coupon-button-*` custom properties on the form's wrapper, which `coupon-button/style.css` applies only while the button has no colour of its own, and `render.php` prints a default button when a saved form has no child.
- **Extra fields and fragments:** `Renderer\CheckoutExtraFields` reads the served layout's extra fields (`LayoutMarkupReader::extra_fields()`), checks them with `Services\ExtraFieldSubmission::collect()` and stores them as order meta on `woocommerce_checkout_create_order`; like the overlay, it runs on any classic checkout. A Key must match `LayoutMarkupReader::EXTRA_FIELD_KEY_PATTERN`, because a leading underscore reaches WooCommerce's internal order setters. `Renderer\CheckoutFragments` swaps the shipping-rate and payment fragments only for sections `LayoutMarkupReader::slots()` finds in the layout; a Slot block's name counts as a section. Order Summary's Items and Totals blocks are found by block name instead (`CheckoutFragments::BLOCK_FRAGMENTS`), so a Slot can't trigger them. When the layout has either, `update_order_review` swaps WooCommerce's `checkout/review-order.php` for the empty `templates/review-order-skipped.php`, so the table WooCommerce would build and the layout would discard never runs, and its review-order hooks fire once. Totals leaves out the shipping rates, which the Shipping Methods block offers (the default layout includes one); Total still counts them, and a layout without that block shows no rate choice. Each review-order hook fires in the block that prints its content: the cart-contents hooks in Items, the order-total hooks in Totals, the shipping hooks in Shipping Methods and the payment hooks in Payment. The Payment block's `layout` (`joined|checkmark|box|grid|cards|lines`) and Methods styles sit on the wrapper as `data-layout` and `--yaycheckout-payment-*`, so they survive `update_order_review`; the gateway list remains WooCommerce's `checkout/payment-method.php`. Items prints divs, not a table, so a row has room for a thumbnail; extensions echo table rows into the cart-contents hooks, so Items wraps any output of each in a table of its own. Items' builder receives the block's attributes, normalised by `CheckoutFragments::order_items_options()`, and the fragment passes the layout's parsed attrs, so the merchant's options survive `update_order_review`. When the Place Order block shows the order total, it also sends `#place_order`: `render.php` prints only the bare button during AJAX (without `woocommerce_order_button_html`, whose extra siblings would repeat), and `checkout.js` swaps it so `data-total` follows the cart.
- **Quantity stepper:** Order Summary Items' `showStepper` option lets the shopper change or remove an item on the checkout, whichever way its `quantityDisplay` shows the quantity. WooCommerce's checkout has no endpoint that sets one item's quantity (its cart form posts the whole cart), so `Renderer\CartItemQuantity` adds the `yaycheckout_cart_item_quantity` wc-ajax action, guarded by a nonce printed on the block wrapper. `CartItemQuantity::apply()` keeps WooCommerce's cart rules: it refuses an unknown item, a quantity above `get_max_purchase_quantity()`, more than one of a sold-individually product and any change `woocommerce_update_cart_validation` vetoes (that filter's error notices become the message), removes the item at 0 and saves through `calculate_totals()`. The stepper and the remove link go through `woocommerce_cart_item_quantity` and `woocommerce_cart_item_remove_link`, so an extension that locks an item's quantity locks it here; the input has no `name` and every button is `type="button"`, so neither posts with the checkout or places the order. `assets/js/checkout-order-summary-items.js` shows a click's quantity at once and sends it 400 ms after the last click, so a run of clicks is one request; it sends the target quantity (never a step, so a repeat can't apply twice), one request at a time, keeps showing quantities not yet sent across a refresh, and holds a Place order click until they are sent. After the last request it fires `update_checkout` rather than building fragments itself, so items, totals, shipping and payment all refresh through `CheckoutFragments` as on any other change; a refused change prints its message under the items and refreshes too, so the row shows the real quantity. When the cart empties, the script sends the shopper to the cart page, since `update_order_review` answers an empty cart with WooCommerce's "session has expired" notice. The script is registered as `BlockRegistry::ORDER_SUMMARY_ITEMS_SCRIPT` and named by the block's `viewScript` for the same reason as the coupon form's: the blocks build can't declare the `wc-checkout` dependency that supplies `wc_checkout_params`, whose `wc_ajax_url` also carries a preview's token.
- **Summary collapsing:** an Order Summary whose direct children include a Summary Header or a Summary Details (the new shape) prints no `#order_review_heading`; one without either prints exactly as before, and its sidebar's **Use header and details** button converts it on request, keeping the heading's text and id. `Services\OrderSummaryCollapse::state()` is the one owner of whether the summary collapses and starts open: four `render.php` files (Order Summary, Header, Details, Toggle) ask it through `of_layout( CheckoutPage::get_instance()->layout() )`, because a Summary Toggle can sit anywhere in the layout and gets no block context from the summary. It is collapsible only with `collapsible` on, a Details to hide, and a Header or a Toggle to open it; `useSummaryCollapse()` in `packages/blocks/src/order-summary/shape.ts` copies the rule for the editor. While collapsible, the Header prints an empty overlay button (`.yaycheckout-order-summary__header-button`) under its own controls, which `packages/blocks/src/order-summary/style.css` lifts above it so links and buttons keep their action, and each Toggle becomes `role="button"` with `data-yaycheckout-summary-toggle`, its links printed as text. `packages/blocks/src/order-summary/view.ts` binds both to the single `#yaycheckout-order-summary-details` and flips its `hidden`, the wrapper's `is-open` and every control's `aria-expanded` together; Details carries none of the classes `CheckoutFragments` replaces, so `update_order_review` leaves it open. The block order is the direction: a Header after Details opens them upward, so the DOM, tab and visual order always match, and the editor's Opens control reads and moves that order.
- **Hide when empty:** a core Group, Columns or Column (`HideWhenEmpty::CONTAINERS`) can watch YayCheckout blocks inside it (`yaycheckoutHideWhenEmpty`, a list of `blockId`s) and hides while every one of them is empty. Only blocks whose `block.json` sets the `yaycheckoutWatchable` support can be watched: Shipping methods (empty when the cart needs no shipping), Payment (when the order needs no payment), Express pay (when `wc_get_pay_buttons()` prints nothing), Slot (when nothing hooked into it prints anything), Field (while WooCommerce's country locale hides it, read by `CheckoutFieldDefaults::hidden_for_country()`), Field Value (while every field it shows is empty; its view script moves the marker as the shopper types and fires `HideWhenEmpty::REFRESH_EVENT`), and Coupon form, Login and Create account (when they print nothing). Each prints `data-yaycheckout-block-id` and, when empty, `data-yaycheckout-empty` on its wrapper through `HideWhenEmpty::wrapper()`; a missing wrapper counts as empty. `Renderer\HideWhenEmpty` filters `render_block_{name}` for each container: it ignores ids no watchable descendant carries, adds `data-yaycheckout-hide-when-empty` and, when `HideWhenEmpty::hidden()` says so, `yaycheckout-hidden-when-empty`, and enqueues `assets/js/checkout-hide-when-empty.js`. The shipping-rate and payment fragments carry `data-yaycheckout-live` and their own empty marker, so after `updated_checkout` the script copies it to the block wrapper and re-applies the rule, which it mirrors from `hidden()`; PHP owns what empty means. A Field's wrapper carries `data-yaycheckout-locale`: on `country_to_state_changing`, after `address-i18n.js` (a dependency) has shown or hidden the row for the new country, the script marks the Field empty while its row is hidden. Coupon form, Login, Create account, Slot and Express pay keep their first-paint marker. A hidden container's required fields still validate. The editor's panel (`packages/blocks/src/shared/hide-when-empty.tsx`, layout editor only) lists each Slot by name and each Field by label and key, warns about them (a watched Field excepted, since it hides only when its own country does), and gives a copied block a new `blockId`.
- **Live values:** a merchant drops cart totals, cart counts and shopper fields into Paragraph and Heading text with the `yaycheckout/live-value` format (`packages/blocks/src/live-value/`). Each is a non-editable span holding `data-yaycheckout-value` (a cart key from `LiveValues::cart_values()`, or `field:<key>`) and `data-fallback`; its text is only the editor's label. `Renderer\LiveValues` filters `render_block_{name}` for each of `LiveValues::BLOCKS` (copied as `LIVE_VALUE_BLOCKS` in `live-value/constants.ts`) on a taken-over checkout only, and returns a block without the class name untouched. `fill()` prints each span's value, or its fallback while the value is empty (0, or a field with no text) and the fallback isn't `''`, and adds `is-empty`. ## Preview links

- `POST /layouts/{id}/preview-link` returns the checkout URL with `?yaycheckout_preview=TOKEN`. `Helpers\PreviewToken` signs the layout, blog and expiry with an HMAC keyed to this purpose and blog, so the token is its own record and minting stores nothing. Anyone with the link can view it; per-link revocation isn't built.
- `Renderer\PreviewRequest` reads the token on `init` and applies its rules on `wp` at 5, before `CheckoutPage`. A preview wins over safe mode.
  - **A bad token:** on the checkout page, a token that doesn't resolve answers 410 instead of falling back to the live layout. A wc-ajax call with such a token does fall back.
  - **Hooks:** the page hooks attach only on the checkout page or a wc-ajax call. The order refusal attaches on any request carrying the argument, valid or not, and covers the classic checkout (`woocommerce_checkout_process`), not the Store API.
  - **Sample products:** an empty cart gets sample products marked with `PreviewRequest::CART_ITEM_FLAG`, saved in the viewer's WooCommerce cart. Any request without the argument strips them.

## Blocks and the embedded editor

- Blocks are dynamic: each `packages/blocks/src/<block>/` has a `block.json` and a `render.php`, and `save()` emits no markup of its own. Leaf blocks return null, and Checkout, Billing, Shipping and Order Summary save only their inner blocks (`saveNestedBlocks()` in `packages/blocks/src/shared/register-dynamic-block.tsx`). So a renamed attribute needs a default in `render.php`, not a block deprecation. `@wordpress/scripts` copies both into `assets/dist/blocks/<block>/`.
- `Blocks\BlockRegistry::register_blocks()` registers every built directory it finds, in `BlockRegistry::ORDER` (the inserter's order), so with no build there are no blocks. `allowed_blocks()` keeps `yaycheckout/*` blocks in the layout editor only, and WooCommerce's Checkout block out of it. In every other editor it turns "all blocks" into the list of blocks registered on the server, so a block registered only in JavaScript is left out. Placement rules live in each `block.json` (`parent`, `ancestor`, `supports.multiple`). Progress and the Next and Previous Step buttons have no ancestor rule, so they can sit outside Checkout. Their storefront scripts fall back to the page's one `.yaycheckout-checkout` (`packages/blocks/src/shared/checkout-root.ts`), and `Renderer\CheckoutProgress` reads step titles from the rendered layout's first Steps block, not from Checkout's block context. Core offers only allow-lists, so Billing, Shipping and Step keep blocks out through `allowedBlocks` built from the registry (`packages/blocks/src/shared/allowed-blocks.ts`). Containers keep core's default appender (the "+" shown while the container or a block inside it is selected), and `checkout/inserter-root.ts` points the header inserter at Checkout only while no block is selected.
- `packages/blocks/webpack.config.js` adds the `live-value/index` and `live-value/view` entries beside the `block.json` ones, which no `block.json` names. `BlockRegistry` enqueues the editor entry and its chip style only in the layout editor, so a page's Paragraph never offers the format, and registers the view entry's handles for `LiveValues::fill()` to enqueue.
- One blocks build serves both editions. It emits a script per block, and `BlockRegistry` passes `isPro`, the post type and the upgrade link as `window.yayCheckoutBlocks`. That global is printed before the Checkout block's editor script (`packages/blocks/src/shared/editor-data.ts`); the live value format's editor script, which runs after it, also reads its `liveValues`.
- `packages/blocks/src/checkout/publish-guard.ts` shows the rules of `LayoutMarkupReader::publish_error()` as a notice, and locks manual saves only while the layout is live: active (from the `yaycheckout/layout-state` store that `layout-actions.tsx` fills, so a stale editor status can't unlock it) or with an edited status of published or scheduled, as the server does; a draft saves freely, and autosave isn't locked. `packages/blocks/src/checkout/layout-actions.tsx` puts Save, plus Activate or Deactivate, in the editor header: Save keeps the status, Activate (held while the rules object) saves unsaved edits first, and both call the `activate` / `deactivate` routes, then reload the post record into the editor so the next save doesn't send the old status. Its Preview opens a `preview-link` in a new tab, which renders the saved markup; unsaved edits don't show. It reads `is_active` from `GET /layouts/{id}`, since `window.yayCheckoutBlocks` is printed before the post is known. `packages/blocks/src/checkout/layout-design.tsx` adds the Layout design sidebar, which edits `Layout::META_DESIGN` through the post's meta, so the header's Save stores it with the markup; it reads the schema from `window.yayCheckoutBlocks.design`, which `BlockRegistry::editor_design_data()` adds only in the block editor. It locks saving while the layout's custom CSS fails the copy of `LayoutDesign::sanitize_custom_css()`, and reprints the canvas's design style (`shared/design-css.ts`, a copy of `DesignStyles::css()`) on every change, including after the canvas iframe is rebuilt. For the picked font it asks `GET yaycheckout/v1/fonts/{slug}` for the canvas's font faces, again after every save: Google's files as a preview until the save uploads the font, then the uploaded ones.
- The admin edits a layout in core's `post.php` editor inside a modal iframe with `?yc-embed=1`. `Engine\Admin\LayoutEditorEmbed` hides the wp-admin chrome and tags the editor's REST calls with `X-YayCheckout-Embed`, and `LayoutCoreRestController::delete_item_permissions_check()` refuses delete for them: after a trash, core navigates the frame to a screen the modal can't host. Drafts save through core's REST API, so autosave and revisions come free. On every layout edit, embedded or not, `Engine\Admin\LayoutEditorCanvas` adds a canvas style through `block_editor_settings_all` that resets the theme's content size, wide size and root padding and hides the title field, so a layout's name is changed from the layouts list's Rename action (`PUT /layouts/{id}`), not in the editor. It also hides the document bar and the Publish date row on layout screens, and the post type leaves out `page-attributes`, so there is no Parent row: the manager and the editor's Activate own a layout's status, and none has a parent. Core's Publish, Save draft, saved state, Switch to draft and Status row are hidden too, but only under `body.yaycheckout-has-layout-actions`, which `layout-actions.tsx` adds once its buttons mount, so a header it can't find leaves core's controls in place. Nothing passes messages between the frame and the SPA: the SPA refetches its layouts when the modal closes, and closing it doesn't ask about unsaved edits.

## Free and Pro

- One codebase, two zips: Free (`yaycheckout/`) without `includes/Pro/`, and Pro (`yaycheckout-pro/`) with it. Pro installs into its own folder, so a wordpress.org update for slug `yaycheckout` can't overwrite a paid install. [The decision record](decisions/2026-10-05-build-time-free-pro-split.md) says why the split is made at build time.
- PHP: `YayCheckout::boot_pro()` requires `includes/Pro/ProServiceProvider.php` when it is readable. The provider calls `Plan::mark_pro()` and attaches through hooks and filters only. `Plan::is_pro()` reports whether it booted, so it can't claim Pro while the files are missing; it describes the build, not a licence. `scripts/check-pro-boundary.sh`, run by `composer lint`, allows exactly one non-comment line naming `YayCheckout\Pro` outside `includes/Pro/`, and that line must be in `includes/YayCheckout.php` (today, in `boot_pro()`).
- SPA: `YAYCHECKOUT_PLAN` becomes `__YAYCHECKOUT_PLAN__` in `apps/admin/vite.config.ts`. With it unset, the dev server uses `pro` and a build uses `free`; `release` sets it from `--plan`. `apps/admin/src/lib/plan.ts` exposes it as `isPro`.
  - Free's upsells are teasers that ship to Free: `ProTag`, `UpgradeButton`, and the `LockedAssignment` mock in `AssignmentDrawer`. They are safe only because Free's PHP has no matching endpoint. `<ProGate>` (`apps/admin/src/components/pro/ProGate.tsx`) would blur its children the same way, but no screen uses it.
  - The template list is the one place the SPA tells the server its plan. `GET /layouts/templates?plan=` marks templates locked for that plan, while creating a layout checks `Plan::is_pro()`.
- Free allows `LayoutRepository::FREE_LIMIT` layouts and Pro is unlimited (`Plan::layout_limit()`). `LayoutRepository::insert_draft()`, behind create, duplicate and import, and `LayoutCapGuard` both ask `Plan::layout_limit_reached()`. After a downgrade from Pro, Free serves the most recently activated layout to every shopper.

## SPA and WordPress

- `Engine\Admin\Settings` enqueues the SPA only on the admin page's hook suffix, `yaycommerce_page_yaycheckout`. `Engine\Register\RegisterFacade` picks `RegisterDev` (Vite at `RegisterDev::DEV_SERVER`, port 3040) while `YAYCHECKOUT_IS_DEVELOPMENT` is true, which is the default, and `RegisterProd` (`assets/dist/admin/`) otherwise, each only if its class exists. So a release zip, which has no `RegisterDev.php`, registers neither unless the site sets the constant to false.
- `Helpers\LocalizeHelper` builds `window.yayCheckoutMeta` (REST root, nonce, site data) and `window.yayCheckoutAdmin` (settings, integrations), each through a filter, and `Engine\Admin\Settings` prints them; Pro adds `store` to the admin data.
- The SPA is a hash-routed React app. `apps/admin/src/lib/api/api.ts` is the ky client, with the REST root and nonce from `yayCheckoutMeta`. Each resource has a zod schema in `apps/admin/src/lib/schema/`, its calls in `apps/admin/src/lib/api/` and its queries in `apps/admin/src/lib/queries/`; the conventions for that bridge are in [conventions.md](conventions.md).
- Production builds one entry into `assets/dist/admin/`, with React and `@wordpress/*` external. The SPA imports the blocks' shared code through the `@blocks-shared` alias.

## Compatibility scan

- `GET /compatibility` (`Controllers\CompatibilityRestController`) composes three live detections and a catalogue, and stores nothing but the catalogue transient.
- **The detections:**
  - `Helpers\StoreEnvironmentHelper` reads versions, the theme, whether the store's checkout is the block checkout, whether safe mode is on, and `checkout_problem`, the reason from `CheckoutHealth::reported_problem()` (empty when there is none or no layout is active).
  - `Helpers\GatewayCompatibilityHelper` lists enabled classic gateways, then active block payment methods with no classic gateway of the same id, flagged `block-only` unless the catalogue gives that id a status, because YayCheckout renders the classic form.
  - `Helpers\CheckoutHookScanHelper` resolves every callback on a fixed list of checkout hooks to a plugin, mu-plugin or theme by its file. Some hooks on its list, such as `woocommerce_before_checkout_form`, are ones the YayCheckout form never fires. It runs inside a REST request, so hooks added only on `wp` or `template_redirect` are invisible. A row hints that a plugin touches checkout, and a missing row doesn't prove that none does.
- **The catalogue:** `Repositories\CompatibilityCatalogueRepository` fetches the remote catalogue at `YAYCHECKOUT_COMPATIBILITY_CATALOGUE_URL` and falls back to the bundled `Support\CompatibilityCatalogue`. A failed fetch, or a document that `normalize()` rejects, caches the bundled list for `CompatibilityCatalogue::TTL_FALLBACK`. A dead endpoint therefore costs one attempt per that period, plus one per Rescan (`?refresh=true`), not one per page view. `normalize()` is the only gate the remote document passes. Statuses include `conflict` (gateways and plugins), which safe mode acts on, and an entry may carry `fixed_in`, the first plugin version without the conflict; `fixed_in` stays out of the wire. `get()` may fetch and is for the admin; the storefront uses `cached()`, the transient or the bundled list.

## Build and release

- `./scripts/run.sh build` type-checks and builds the SPA, then the blocks. Both must build for a release: without the blocks build, a zip ships an editor with no YayCheckout blocks.
- `./scripts/run.sh release`, in order:
  1. Sets the version when one is passed or typed: the `yaycheckout.php` header, `YAYCHECKOUT_VERSION`, and `Stable tag:` in `readme.txt`.
  2. Runs the admin-shell prerelease sync, exports `YAYCHECKOUT_PLAN` and builds.
  3. Copies a fixed list into a folder named after the edition. Free deletes `includes/Pro/`; Pro renames the plugin in its header.
  4. Strips `RegisterDev.php`, `assets/dist/admin/.vite`, source maps, `.DS_Store` and `.gitkeep`.
  5. Zips into `release/`, and checks the zip for `includes/Pro/` entries against the plan.
  - It runs no lint, boundary check or tests.
- The copy list is the release: a runtime file outside it is silently absent from the zip. The list and its strip step live in `cmd_release` in `scripts/run.sh`.
