# Architecture

**Purpose:** how YayCheckout's parts fit together: boot, the admin-shell sync, the server layers and who writes what, how a layout is stored and picked, the storefront, preview links, blocks and the embedded editor, the Free/Pro split, how the admin SPA reaches WordPress, the compatibility scan, release, and tests. Each claim names the file that decides it; read that file for the details.

**Update when:** a change moves a boundary described here: boot order or autoloading, the admin-shell sync, a layer or a writer, a stored option or post field, how the storefront picks or renders a layout, the preview rules, how blocks register or which editor offers them, the Free/Pro seam or its checks, how the SPA loads or calls WordPress, the compatibility scan, the release steps, or the test harness. A feature that stays inside an existing layer needs no update.

Commands and hard rules live in [CLAUDE.md](../CLAUDE.md). Citations give a path and a symbol, not a line number: search for the symbol. Where the code has a known gap, this doc states the behaviour as it is today.

## Boot and autoload

- `yaycheckout.php` is the entry point. Each of its constants is defined only when not already defined, so `wp-config.php` can override any of them. `YAYCHECKOUT_IS_DEVELOPMENT` is the one a site sets (see [SPA and WordPress](#spa-and-wordpress)).
- Two autoloaders run. `composer.json` classmaps only the scoped admin-shell in `vendor-prefixed/src/` and `YayCheckoutPluginAdapter.php`; `yaycheckout.php` requires `vendor/autoload.php` unconditionally, then the adapter file directly. Product classes in the `YayCheckout\` namespace go through the loader in `yaycheckout.php`, which maps them onto `includes/`, requires a file only if it exists, and uses `require_once` because a doubled backslash in a class name maps to the same file. `boot_pro()` requires `ProServiceProvider.php` by path, and Composer's `autoload-dev` maps `YayCheckout\Tests\` to `tests/`.
- That `file_exists` check lets one tree run with parts missing: Free has no `includes/Pro/`, and release zips have no `RegisterDev.php`, so code checks for those classes first (`is_readable` in `YayCheckout::boot_pro()`, `class_exists` in `RegisterFacade`) and names them only behind that check.
- Boot runs on `plugins_loaded`:
  - priority 5: admin-shell boots and registers the adapter (see [the next section](#admin-shell-sync-and-scoping));
  - priority 10: `plugin_init()` shows a notice and stops if WooCommerce is missing. Otherwise it declares HPOS compatibility (`Engine\ActDeact::before_woocommerce_init`), builds the `YayCheckout` singleton and loads translations.
- `includes/YayCheckout.php` wires everything by hand in its constructor, with no container. `boot_pro()` runs first so `Support\Plan::is_pro()` is settled before any component reads it; then REST, asset registration, the admin page, blocks, the post type, the layout guards, the editor embed, and the storefront renderers.
- Activation stores nothing: settings and each layout's design derive from their schemas on read. `uninstall.php` deletes layouts and options named `yaycheckout_*` only when the merchant turned on `general.delete_data_on_uninstall`; the catalogue transient, extra-field order meta and the other sites of a network stay behind. It runs without the autoloader, so it repeats those keys as literals.

## Admin-shell sync and scoping

- Admin-shell is a private Composer package shared by the YayCommerce plugins. It draws the shared YayCommerce admin menu and its common pages, and adds this plugin's submenu entry.
- Every plugin ships its own copy, so php-scoper rewrites the package into `vendor-prefixed/` under the `YayCheckoutScoped` namespace (`scoper.inc.php`). [The decision record](decisions/2026-10-05-admin-shell-scoped-with-php-scoper.md) says why. With several YayCommerce plugins active, the newest copy draws the shared menu.
- `YayCheckoutPluginAdapter.php` joins the two. It is a global class that implements the scoped menu-adapter interface and stays out of scoping. It names the page slug `yaycheckout` and the capability `manage_woocommerce`, and its page callback prints the SPA's mount point, `<div id="yaycheckout">`.
- The sync lives in the package's own scripts. `./scripts/run.sh dev` runs a full `composer update`, then `vendor/bin/yaycommerce-update`, which deletes `vendor-prefixed/`, updates admin-shell, requires php-scoper and thecodingmachine/safe as dev dependencies (which can rewrite `composer.json`), regenerates `scoper.inc.php` from the package's template keeping only the prefix and the adapter's name, then scopes the package and dumps the classmap.
- `./scripts/run.sh release` runs the `yaycommerce-prerelease` variant, which ends with `composer install --no-dev`. A plain `composer install` never builds `vendor-prefixed/`.

## Server layers and write ownership

- REST lives under `BaseRestController::REST_NAMESPACE` (yaycheckout/v1). `Engine\RestAPI` builds the Free controllers on `rest_api_init`; `Pro\ProServiceProvider::rest_endpoints()` builds the Pro ones, so the Free build simply has no such route. Every route, ours and core's, requires `LayoutPostType::CAPABILITY` (`manage_woocommerce`).
- Callbacks run through `BaseRestController`: `exec_read`, `exec_write_wp` for WordPress API writes, and `exec_write`, which wraps a SQL transaction, for custom tables. There are no custom tables, so nothing uses `exec_write`. WordPress writes go through the object cache, and a `ROLLBACK` would leave a persistent cache holding rolled-back data; ordering the writes so a partial failure leaves a safe state is the substitute. `LayoutRepository::archive()` deactivates before it trashes, so a refused trash leaves the layout deactivated but not archived. A thrown exception becomes a 500, its message goes back to the client, and `Helpers\Logger::exception()` logs it.
- The layers under `includes/`:
  - `Models/` are values that own their schemas and the storage keys of what they describe, and validate input against those schemas;
  - `Repositories/` hold every option call, most post and meta calls, and the invariants of their own writes;
  - `Services/` compute on data a caller already fetched, with no storage calls (`LayoutMarkupReader`, `LayoutAssignment`, `RequiredFieldOverlay`, `RequiredIndicator`, `ExtraFieldSubmission`);
  - `Controllers/` are thin, apart from `LayoutCoreRestController`, which gates core's layout routes, and `LayoutTemplateCatalogue`, which isn't a controller but the template list and its plan rule;
  - `Renderer/` hooks the storefront;
  - `Engine/` holds activation, REST and asset wiring, the admin page, the editor embed and the layout guards, which enforce the repositories' rules on core's paths with their own post and meta calls.
- Writers: `LayoutRepository` writes layouts (with their `Layout::META_TEMPLATE` and their guest view posts, `Layout::GUEST_VIEW_POST_TYPE`) and the active set; `SettingsRepository` writes `yaycheckout_settings` and its flags (`yaycheckout_settings_updated_at`, `yaycheckout_reviewed`, `yaycheckout_setup_done`); core's REST API (wp/v2) writes `post_content`, the layout's design (`Layout::META_DESIGN`) from the editor, and a guest view post's `post_content` from its own editor (every write of it filtered by `LayoutPostType::sanitize_guest_view()`); `CompatibilityCatalogueRepository` caches the catalogue in a transient; `Renderer\CheckoutExtraFields` writes extra-field order meta when the order is created, and remembered extra-field values to the WooCommerce session (`CheckoutExtraFields::SESSION_VALUES`) until then; `Engine\LayoutTrashSync` deletes core's trash timestamp; `Renderer\PreviewRequest` puts a preview's sample products in the viewer's cart; `Renderer\CartItemQuantity` changes cart item quantities and removes items from the shopper's cart through its wc-ajax action; `FontRepository` uploads a layout's design font into core's Font Library (`wp_font_family` and `wp_font_face` posts, files in `wp_get_font_dir()`), called by `Engine\DesignFontInstall` when a design is saved (the design meta written by any writer, and every editor Save) ([why](decisions/2026-10-11-picked-fonts-installed-into-font-library.md)).
- `Models\Settings::schema()` describes every setting and `Models\LayoutDesign::schema()` every design token, each with its type and default. `Settings::from_option()` and `LayoutDesign::from_meta()` project what is stored through the schema, so a missing, stale or invalid value reads as its default and neither the SPA nor the editor meets an unknown shape; `Settings::sanitize()` checks a settings write against the same schema, and `LayoutDesign::rest_schema()` a design write.
- `POST /setup` (`Controllers\SetupRestController::complete_setup()`) validates the template before its first write, then creates the draft from it and marks setup done. Once setup is done it answers 409, so a later retry can't add a second draft; two overlapping requests both pass the check. A re-run from Settings sends `rerun`, which skips that check and always adds a draft. `LayoutTemplateCatalogue::assert_available()` decides which templates a plan may pick, and the draft is built from the picked one. `POST /mark-setup-done`, the wizard's Skip, sets the flag without a layout.

## Layouts: one post, a status and an active set

- A layout is one `yay_checkout_layout` post (`PostTypes\LayoutPostType`): `post_content` holds the block markup, and `post_status` says whether shoppers may see it. Its design is the `Layout::META_DESIGN` meta (`Models\LayoutDesign`), the only design there is: every section of `LayoutDesign::schema()` (colours, typography, inputs, checkboxes, radios, help text) with every token, plus custom CSS. Any token may be empty (`''`, or `null` for a size or radius), and an empty token prints nothing, so the theme shows through, except an empty base size, which prints `DesignStyles::DEFAULT_BASE_SIZE` (13px) ([decision record](decisions/2026-10-13-empty-base-size-prints-13px.md)). A colour is a hex colour or a theme preset's `var(--wp--preset--color--<slug>)`, and the background (a `fill`) may also be a gradient, written out to `LayoutDesign::GRADIENT_PATTERN` or a `var(--wp--preset--gradient--<slug>)`. The patterns refuse anything that could end a declaration, since tokens print unescaped, and the storefront and the editor canvas both define the preset properties. The colour tokens are themselves offered to blocks as palette presets: `layout-design.tsx` adds "Design: Primary" and the rest (slug `yaycheckout-<token>`) first in every colour picker's user palette (`color.palette.custom`) through `blockEditor.useSetting.before`, and relabels that group from Custom to Checkout unless the merchant has a Global Styles palette of their own, since core groups swatches only by origin; since the post editor rebuilds its palette from the theme's global styles over REST and drops a `block_editor_settings_all` one, and `assets/css/design-presets.css` defines `--wp--preset--color--yaycheckout-<token>` and its `has-*` classes, so a block that picks one follows later Design changes. A token can't name one of them (`LayoutDesign::DESIGN_PRESET_PREFIX`), since each reads a token. It is registered in REST with a schema built from `LayoutDesign::schema()`, so core refuses an invalid token. `LayoutRepository::duplicate()` copies it with the rules, and Pro's export file carries it; import (`LayoutImportReview::from_envelope()`) projects it through `LayoutDesign::from_meta()` instead of refusing the file, so a missing or malformed section imports as empty. [The decision record](decisions/2026-10-05-layout-is-one-post.md) says why. Publishing is a status change, the same one `activate()` and cron's `publish_future_post` make; the wire `status` is `post_status` (`Enums\LayoutStatus`). Merchants never see it: the SPA, the editor and the preview banner show Active (in the active set), Inactive or Archived ([decision record](decisions/2026-10-08-deactivate-unpublishes.md)).
- A new layout, and the setup wizard's, starts from a template in `LayoutTemplateCatalogue`: `templates/layouts/<slug>/markup.php` gives its blocks, `design.json` its `Layout::META_DESIGN` with every section set, and `Layout::META_TEMPLATE` (`_yaycheckout_template`) records the slug. A template missing either file is listed as Coming soon (`available: false`) and refused. Each template also has a `preview.html`, the mock's page with its scripts stripped, captured by `./scripts/run.sh previews` (`scripts/capture-template-previews.py`); `templates()` lists its URL as `preview_url` (`''` without one) in the catalogue `LocalizeHelper` prints, and the picker shows it in a sandboxed iframe that may not run scripts. Availability ignores it. Blank is `LayoutTemplateCatalogue::DEFAULT_SLUG`, Classic two-column. Duplicate copies the slug and import leaves it unset. Reset (`LayoutRepository::reset()`) puts back the markup and design of the layout's template, or of the default when it has none still available, without the plan lock; the old markup stays as a revision, but the design meta has none. Classic two-column is a white header bar (logo or site title, a Cart › Checkout › Order received breadcrumb, "Secure checkout") over a constrained Group (1120px) holding the Checkout block with a two-column Columns: the form left (Express Pay, a contact row with Login, Email, Billing, Shipping, Shipping methods, Payment, Order Note, then the terms sentence, Terms & Privacy, Place Order and Return to cart), and right a sticky Group holding a white card with Order Summary (Items, Coupon Form, Order Summary Breakdown, Order Summary Total, with room for the merchant's blocks around them) and the privacy and terms links. It has no footer, and the terms sentence and links print only for the pages that exist. Its look comes from block settings, not plugin CSS: the summary sticks only where the theme's settings enable sticky positioning, and on phones the columns stack form first. Its logo, links and labels are fixed at creation. Upsell & cross-sell has the same header with "Free shipping over $150" and "30-day returns" beside "Secure checkout", and the form as white cards (contact with Login and Email; the main address, holding Different Address and the other address when billing is main; Shipping methods; Payment, holding Different Address and Billing when shipping is main, then the terms sentence, Terms & Privacy and Place Order) beside a sticky summary card whose Items has the quantity stepper and which ends with a Savings note; the mock's order bump, free-shipping bar and cross-sell list have no block yet and are left out. Accordion one-page is a 640px column: a header (Back, logo or site title, Secure), "Checkout" with a text Steps Progress, four accordion step cards (Contact with Email; Delivery address with the main address, Different Address and the other address; Shipping options with methods and Order Note; Payment with the terms sentence and Terms & Privacy, kept out of the pinned bar so its text can't push Place Order off the right), and a Group pinned to the bottom holding a collapsible Order Summary that opens upward (Items, Coupon Form, Breakdown) beside a Continue that hides on the last step and a Place Order that shows only then. Minimal steps is a 440px column under a full-width bar Steps Progress: logo or site title with a text Steps Progress ("Step N of 3"), a collapsible Order Summary (item count toggle and total in the header; Items without thumbnails and Breakdown without subtotal when open), then three one-at-a-time steps (Address with Email and the main address only; Delivery with Shipping methods and a To review row; Payment with a grid of methods, the terms sentence and Terms & Privacy), Continue / Back / Pay and Secure checkout with Return to cart in a Group pinned to the bottom of the screen.
- The post type maps every capability to `manage_woocommerce` with `map_meta_cap => false`. `Controllers\LayoutCoreRestController` is its `rest_controller_class`: it requires the capability for reads too, because core answers a logged-out read of a published post, and its `prepare_item_for_database()` refuses a wp/v2 save that would leave a layout published or scheduled while `LayoutMarkupReader::publish_error()` objects. wp-admin's Quick Edit and Bulk Edit don't pass through it, so they can publish such a layout.
- `LayoutRepository::publish()` and `activate()` also refuse on `publish_error()`, and refuse an archived layout, since setting its status would restore it from the trash. `publish()` goes through `wp_publish_post()`, so a scheduled or pending layout goes live at once; `activate()` publishes first unless the layout already is, and checks the rules either way. `deactivate()` drops the layout from the active set and moves a published, pending or scheduled layout to draft; Free's `set_active()` deactivates the layout it replaces the same way. Layouts published but inactive from before this rule stay published and show as Inactive.
- The active set is the `Layout::OPTION_ACTIVE` option, an ordered list of ids, and shoppers see only layouts in it. `LayoutRepository::active()` doesn't re-check `post_status`: it relies on `LayoutActiveGuard` (below) to drop a layout that stops being visible, and an active layout that becomes scheduled keeps serving its current content. Free keeps one (`set_active()` replaces it, and `active_ids()` reads only the last id stored); Pro keeps several, most recently activated last.
- Guards keep the set honest (`includes/Engine/`):
  - `LayoutActiveGuard` refuses to trash or delete an active layout, and drops one whose status moves to anything but published or scheduled (draft, pending or private). It and `LayoutTrashSync` call `LayoutRepository::forget_active()`, which leaves the status alone, because `deactivate()` would change it again inside the transition;
  - `LayoutTrashSync` removes WordPress's trash timestamp, so an archived layout is never purged by cron;
  - `LayoutCapGuard` enforces the Free limit (`LayoutRepository::FREE_LIMIT`) on core's wp/v2 insert, because any shop manager can POST there directly. It misses a layout started from wp-admin's `post-new.php`, which core inserts as an auto-draft and the editor then saves as an update, and `LayoutRepository::count()` leaves private layouts out.
- `LayoutRepository::archive()` deactivates before it trashes. With `EMPTY_TRASH_DAYS` set to 0, core's `wp_trash_post()` deletes instead, so archiving deletes the layout. `restore()` doesn't check the limit. `delete()` refuses a layout that isn't archived; core's wp/v2 `DELETE ?force=true` doesn't check.
- The layouts list's bulk actions go through `POST /layouts/bulk` (`LayoutRepository::bulk()`). It runs deactivate, archive, restore or delete on each id, and answers with the ids that ran and the ids refused, with each one's message. One refusal doesn't stop the rest. Unlike `archive()`, a bulk archive refuses an active layout instead of deactivating it, so a selection can't stop a layout serving unless the merchant chose to deactivate it.
- Layout lists are paged server-side (`Models\LayoutQuery::PER_PAGE`), and search matches titles only (`LayoutRepository::match_search_to_title()`), since `post_content` is markup. The lists show only listed statuses and the archive, so a private layout appears in neither.

## Storefront

- `Renderer\CheckoutPage` takes over the checkout page on `wp` when safe mode is off and a layout resolves. The order-received and order-pay endpoints stay WooCommerce's (`CheckoutPage::on_checkout_page()`). Otherwise WooCommerce is untouched, except that the opt-in `advanced.force_enqueue_checkout_scripts` setting (`Renderer\CheckoutScripts`) still loads WooCommerce's checkout scripts. A preview link resolves its own layout first (see [Preview links](#preview-links)).
- **Admin bar:** on a page `CheckoutPage::takes_over()`, `Renderer\CheckoutAdminBar` removes core's Edit Page and Edit site items, which edit neither the page nor the template shown, and gives users with `LayoutPostType::CAPABILITY` an Edit Layout item that opens the rendered layout (the previewed one on a preview link) in the SPA's editor (`Helpers\AdminUrlHelper::edit_layout()`).
- **Which layout:** `LayoutRepository::active()` gets the shopper facts that `CheckoutPage` reads (roles, logged in, `wp_is_mobile()`). Free serves its one active layout and ignores its rules; Pro hands the set to `Services\LayoutAssignment::pick()`, most recently activated first, which serves the first layout whose rules match (groups ORed, conditions ANDed; no rules matches everyone). No match leaves WooCommerce's checkout.
- Every request picks afresh, AJAX and the order submit included, with no pin, and nothing in the checkout POST says which layout rendered the form. Each `Enums\ConditionType` reads a fact that holds for the life of a form, so the shopper can't swap the layout mid-form; a fact the shopper can change, such as billing country or cart, must never become a condition. A merchant's change between render and submit (activating, editing the markup or rules, safe mode) still changes the layout the order is validated against.
- **Rendering:** `template_include` at `PHP_INT_MAX` swaps in `templates/checkout-page.php`, which renders the layout before `wp_head()` (block themes print the import map there), inside the template's own document, on every theme: no theme header or footer, while `wp_head()` still loads the theme's styles. No page title is printed. `CheckoutPage` dequeues WooCommerce's `woocommerce-general`, `woocommerce-blocktheme`, `woocommerce-layout` and `woocommerce-smallscreen` and loads `Renderer\CheckoutBaseStyles`: `assets/css/checkout-base.css`, the design font's `@font-face` rules (`Renderer\DesignFonts`, from its Font Library install; none when the theme loads the font itself), then the design. The base removes the theme's horizontal margin, padding and max-width around the layout and resets the theme.json content size, wide size and root padding inside it, so only the layout's own blocks limit its width; it also styles what several blocks or WooCommerce itself print (field rows, inputs, select2, checkboxes, notices, the blockUI spinner, buttons). Markup one block alone prints is styled in that block's `style.css`; Payment and Shipping methods each draw their own rows, with no shared partial. The `checkout` block prints WooCommerce's `<form name="checkout">`, and every section block sits directly inside it; nothing stops the Checkout block itself being nested. `Renderer\DesignStyles` prints the rendered layout's design (`Models\LayoutDesign`) as `--yaycheckout-*` custom properties, one for each token that isn't empty plus the font size, which is 13px while its token is empty, then a page rule for the page's background, text colour and font, with a font a heading rule that makes the checkout's headings inherit it (a gradient background prints as `--yaycheckout-background-gradient` and the page's `background-image`, never as `--yaycheckout-color-background`, so inputs and rows keep their solid fallback; inputs read `--yaycheckout-input-background` first, then `--yaycheckout-color-background`, and `--yaycheckout-input-border-color` first, then `--yaycheckout-border-color`; a focused input recolours its border and draws a flush ring in `--yaycheckout-input-focus-color`, falling back to `--yaycheckout-primary-color`, `--yaycheckout-input-focus-ring-width` wide, falling back to 1px (the Thin border focus style prints 0), and fills with `--yaycheckout-input-focus-background`, falling back to the input background; field labels, floating ones included, read `--yaycheckout-input-label-color`, then inherit (a floating label then falls back to `--yaycheckout-input-color`); the help text under every kind of field reads `--yaycheckout-help-text-color` and `--yaycheckout-help-text-size`, falling back to the inherited colour at 75% and 0.875em; a checkbox reads `--yaycheckout-checkbox-size`, `-radius`, `-border-width` and `-checked-color`, falling back to 16px, `--yaycheckout-neutral-radius`, 1px and `--yaycheckout-primary-color`; while unticked, a checkbox reads `--yaycheckout-checkbox-border-color` and `--yaycheckout-checkbox-background`, falling back to `--yaycheckout-input-border-color` and `--yaycheckout-input-background`; a loose radio reads `--yaycheckout-radio-size`, `-border-width`, `-border-color`, `-background` and `-checked-color`, falling back to 18px, 1px, the input border, the input background and `--yaycheckout-primary-color`; Payment and Shipping's drawn indicators fall back to `--yaycheckout-radio-border-color` and `--yaycheckout-radio-checked-color` under their block's own Radio colours), then the site-wide custom CSS (the setting `advanced.custom_css`, Settings → Advanced) and the layout's, each checked on print so a rejected one drops only itself. Tokens are values, never selectors: the base and block CSS read each property with a neutral fallback that follows the theme, so an empty token prints nothing; the font size is the one exception. `LayoutEditorCanvas` loads the same base and the edited layout's tokens into the editor canvas, without either custom CSS.
- **Fields:** the Field and Email blocks call `woocommerce_form_field()` with the value classic checkout prints, `WC()->checkout()->get_value()` (the session, or the account when logged in), so a reload keeps what the shopper typed. `Renderer\CheckoutFieldDefaults` also gives each billing or shipping row WooCommerce's `address-field` and `update_totals_on_change` classes from `woocommerce_checkout_fields`, which `checkout.js` needs to send typed address changes to `update_order_review`; layout classes such as `form-row-first` are left out. A collapsed field that holds a value prints open. Which address is the main one follows WooCommerce's `woocommerce_ship_to_destination` (`Renderer\CheckoutDifferentAddress::destination()`). When billing is main, the Different address block prints WooCommerce's own `ship_to_different_address` checkbox, and the Shipping block's `shipping_address` class lets `checkout.js` show it and send its rates fields while the box is ticked. When shipping is main, the Shipping block prints WooCommerce's box checked and hidden, and the Different address block prints "Use same address for billing" (`yaycheckout_same_billing`): `assets/js/checkout-different-address.js` hides Billing and mirrors Shipping into it, and `CheckoutDifferentAddress` copies the posted shipping address into billing and makes billing's address fields optional for that request. A layout with no Different address block always saves Shipping as typed; one with no Billing section, when shipping is main, always copies it into billing. With `billing_only`, or a cart that needs no shipping address, neither block prints and WooCommerce copies billing into shipping. Of WooCommerce's form hooks, only those around the payment methods and Place order fire; `woocommerce_before_checkout_form`, the customer-details pair, `woocommerce_checkout_billing` and `woocommerce_checkout_shipping` (account fields, order notes) never do. The Create account block prints the account part of form-billing.php when WooCommerce allows registration at checkout and the visitor is a guest: the `createaccount` checkbox while guest checkout is on, then `get_checkout_fields( 'account' )` through `woocommerce_form_field()`, between `woocommerce_before_checkout_registration_form` and `woocommerce_after_checkout_registration_form`. `WC_Checkout::process_customer()` creates the account, and WooCommerce's `checkout.js` toggles the fields. A layout without the block still has WooCommerce require the account fields when guest checkout is off. The Order note block prints `order_comments` through `woocommerce_form_field()`, with Field's Show field and Required settings; `RequiredFieldOverlay::apply_order_note()`, run by `CheckoutRequiredFields`, makes WooCommerce require the note exactly when the block does, and WooCommerce saves it as the order's customer note. The Additional fields block prints the `woocommerce-additional-fields` part of form-shipping.php without its heading: `get_checkout_fields( 'order' )` between `woocommerce_before_order_notes` and `woocommerce_after_order_notes`, while `woocommerce_enable_order_notes_field` allows it. It leaves out `order_comments` when the layout has an Order note block.
- **Login:** The `yaycheckout/login` block (`Renderer\CheckoutLogin`) prints a sentence only when `woocommerce_enable_checkout_login_reminder` is `yes` and the shopper is logged out. The editor reads that option from `window.yayCheckoutLogin`. The merchant selects which phrase is the control (a span with `CheckoutLogin::TRIGGER_CLASS` in `text`, read by `CheckoutLogin::trigger_parts()`) and whether it links to `wp_login_url( checkout )` or opens a modal; a block that still has plain `text` and `linkText` uses `CheckoutLogin::split_link()`. The modal's form lives in a `<template>` and is moved to `document.body`, so it is not nested in `<form name="checkout">`. `wc_ajax_yaycheckout_login` calls `wp_signon()`; the next request, `wc_ajax_yaycheckout_login_state`, returns the logged-in layout id, account values for empty fields, and fresh `update-order-review` and `woocommerce-process_checkout` nonces. The form keeps its node: the script fills empty fields, removes the reminder, and fires `update_checkout`. It reloads the page when `form.checkout` is missing (guest checkout and registration both off: the reminder prints above "You must be logged in to checkout.") or when `data-yaycheckout-layout` differs from the logged-in layout id. New layouts include one Login in their guest view, which prints it whatever the reminder option says; the merchant adds any other.
- **Terms and privacy:** the `yaycheckout/terms` block (Terms & Privacy) prints WooCommerce's `checkout/terms.php`: the checkout privacy text, and the required terms checkbox when a Terms page is set, with WooCommerce's terms hooks. It prints nothing without a cart or when WooCommerce has nothing to show. Place Order prints only the button, the review-order submit hooks and the nonce, so the terms never share its row. Nothing adds the block for the merchant: a layout without it has no privacy text and no terms checkbox, and with a Terms page set WooCommerce refuses every order. Every template ships it.
- **Validation:** `Renderer\CheckoutRequiredFields` filters `woocommerce_checkout_fields` at 9999 through `Services\RequiredFieldOverlay::apply()`, so a billing or shipping field is required exactly when its block says so, over WooCommerce's country rules too, and any email field always is; billing and shipping fields the layout leaves out become optional. Why a field or address section is out of use for the request (the country locale hides it, billing copies shipping, the order uses no such address) is answered by `Renderer\CheckoutFieldUsage`, read by `CheckoutRequiredFields`, `CheckoutDifferentAddress` and `CheckoutExtraFields`; a new reason is added there. The filter isn't gated on the checkout page, because the checkout POST validates before `is_page()` works, so it applies to any classic checkout form on the site. `assets/js/checkout-field-requirements.js` re-applies flags and labels after WooCommerce's `address-i18n.js` resets them on a country change.
- **Remember value:** an Extra field block with `rememberValue` on carries `data-yaycheckout-remember`. On a change in one, `extra-field/view.ts` posts the checkout form to `wc_ajax_yaycheckout_remember_extra_fields`, guarded by WooCommerce's `update-order-review` nonce from `wc_checkout_params`. `CheckoutExtraFields::remember()` cleans the remembered Keys with `ExtraFieldSubmission::collect()` and replaces `SESSION_VALUES`; It also answers `woocommerce_checkout_get_value` for remembered Keys (`''` when nothing is stored, so customer meta under the same Key never leaks in), so `render.php` reads them through `CheckoutFieldDefaults::value()` like the Field block, and `RevealLink::collapsed()` prints a field holding a value open. `persist()` clears them once the order is created. Off by default, so existing layouts keep their behaviour until the merchant turns it on.
- **Coupon form:** the `coupon-form` block has no `parent`, so it can sit inside the checkout form or beside it, and it prints no `<form>` of its own because forms can't nest. WooCommerce's `checkout.js` applies a coupon only on a `form.checkout_coupon` submit, so `assets/js/checkout-coupon-form.js` posts to WooCommerce's `apply_coupon` endpoint itself, prints the response's notices under the field and fires `update_checkout`; `CheckoutFragments::drop_applied_message()` empties Woo's own success message for that request only (it posts `CheckoutFragments::COUPON_FORM_FIELD`; the cart page's `cart.js` hits the same endpoint without it), so only errors and other extensions' notices print. Applied coupons show as chips under the field, built by `CheckoutFragments::coupon_chips_html()`, which `CheckoutFragments::fragments()` refreshes on every `update_order_review` (`COUPON_CHIPS_CLASS`) without touching WooCommerce's review-order table. A chip's × is WooCommerce's `.woocommerce-remove-coupon` link, so `checkout.js` removes the coupon, and on a layout with a Coupon form, Order Summary Breakdown's coupon rows print `coupon_amount_html()` through `woocommerce_cart_totals_coupon_html`, without `[Remove]`; without one they keep Woo's row. Applied coupons are the field's value for `Disclosure::mode()`, so the form prints shown and its chips stay visible after a reload. The field carries no `input-text` or `form-row` class, so WooCommerce's inline validation leaves it alone, and the script catches Enter, which would otherwise submit the checkout. The script is registered as `BlockRegistry::COUPON_FORM_SCRIPT` and named by the block's `viewScript`, so core loads it only where the block renders; a handle, not `file:`, because the blocks build can't declare the `wc-checkout` dependency that supplies `wc_checkout_params`. Like WooCommerce's own coupon form, the block renders nothing when coupons are off or a guest must log in first. The Apply button is the `coupon-button` child block, which the form's template locks in, so its style supports (colour, typography, border, spacing, Fill or Outline) land on the `<button>`; the script still finds it by `.yaycheckout-coupon-form__apply`. The form's Button colors reach it as `--yaycheckout-coupon-button-*` custom properties on the form's wrapper, which `coupon-button/style.css` applies only while the button has no colour of its own, and `render.php` prints a default button when a saved form has no child.
- **Guest view:** a guest WooCommerce gives no checkout form (`CheckoutLogin::must_log_in()`: logged out, guest checkout off and "During checkout" account creation off) sees the layout's guest view. It is the `post_content` of a published `Layout::GUEST_VIEW_POST_TYPE` (`yay_checkout_guest`) post whose `post_parent` is the layout, registered in `PostTypes\LayoutPostType` with revisions and the layout's REST controller (whose publish rule skips it) and capabilities, and limited to `Layout::GUEST_VIEW_BLOCKS` on every write by `LayoutPostType::sanitize_guest_view()` (`wp_insert_post_data`). `LayoutRepository` reads and writes it (`guest_view_id()`, `guest_view()`, `save_guest_view()`): create and Reset write `templates/layouts/guest-view.php` (`LayoutTemplateCatalogue::guest_view()`), duplicate and Pro's import copy it, `delete()` and `uninstall.php` remove it, and Pro's export carries it as `layouts[0].guest_view`. `packages/blocks/src/checkout/render.php` prints it, rendered by `CheckoutLogin::render_guest_view()`, in a `<div class="… yaycheckout-checkout--guest">` in place of the `<form>`, so `checkout.js` never attaches; a Login inside it prints whatever the reminder option says (`CheckoutLogin::in_guest_view()`). With no guest view, the old Login and sentence print. A preview link with `yaycheckout_view=guest` (`PreviewRequest::VIEW_ARG`, honoured only with a valid token) makes `must_log_in()` true. In the editor it is a post of its own in core's editor: `BlockRegistry::allowed_blocks()` offers only the allowed blocks, `LayoutEditorCanvas` gives it its layout's design, and the header's "Checkout form | Guest view" switch (`packages/blocks/src/checkout/layout-view.tsx`) opens the other post in the same frame, asking to save first, from the editor URLs in `window.yayCheckoutBlocks.guestView` (with `LayoutEditorEmbed::QUERY_FLAG` on an embed request, and `location.replace()` so closing the manager's dialog stays one click), which also gives a layout opened without a guest view the default one ([decision record](decisions/2026-10-14-guest-view-in-child-post.md)).
- **Extra fields and fragments:** `Renderer\CheckoutExtraFields` reads the served layout's extra fields (`LayoutMarkupReader::extra_fields()`), checks them with `Services\ExtraFieldSubmission::collect()` and stores them as order meta on `woocommerce_checkout_create_order`; like the overlay, it runs on any classic checkout. An extra field may sit anywhere in the layout, Billing and Shipping included; one inside an address section the order doesn't use (Shipping when the shopper keeps one address or the cart ships nowhere, Billing when it copies Shipping) is neither validated nor stored, as WooCommerce ignores that section's own fields. A Key must match `LayoutMarkupReader::EXTRA_FIELD_KEY_PATTERN`, because a leading underscore reaches WooCommerce's internal order setters. `Renderer\CheckoutFragments` swaps the shipping-rate and payment fragments only for sections `LayoutMarkupReader::slots()` finds in the layout; a Slot block's name counts as a section. Order Summary's Items, Order Summary Breakdown, Order Summary Total and Savings note blocks are found by block name instead (`CheckoutFragments::BLOCK_FRAGMENTS`), so a Slot can't trigger them. When the layout has any of them, `update_order_review` swaps WooCommerce's `checkout/review-order.php` for the empty `templates/review-order-skipped.php`, so the table WooCommerce would build and the layout would discard never runs, and its review-order hooks fire once. Order Summary Breakdown leaves out the shipping rates, which the Shipping Methods block offers (the default layout includes one); the order total still counts them, and a layout without that block shows no rate choice. Shipping Methods prints its own rate list from `WC()->shipping()->get_packages()`, not WooCommerce's `shop_table` or `wc_cart_totals_shipping_html()`: each rate keeps WooCommerce's `shipping_method` input and runs `woocommerce_after_shipping_rate`, and the review-order shipping hooks wrap any plugin `<tr>` output in a table beside the list. `woocommerce_cart_shipping_method_full_label` receives only the method name; the price is a separate element with the same tax and zero-cost rules as `wc_cart_totals_shipping_method_label()`. Each review-order hook fires in the block that prints its content: the cart-contents hooks in Items, the order-total hooks in Order Summary Breakdown (Order Summary Total prints only its row and may repeat, its fragment selector hashed from its options), the shipping hooks in Shipping Methods and the payment hooks in Payment. The Payment block's `layout` (`joined|checkmark|box|grid|cards|lines`) and Methods styles sit on the wrapper as `data-layout` and `--yaycheckout-payment-*`, so they survive `update_order_review`; the gateway list remains WooCommerce's `checkout/payment-method.php`. Items prints divs, not a table, so a row has room for a thumbnail; extensions echo table rows into the cart-contents hooks, so Items wraps any output of each in a table of its own. Items' builder receives the block's attributes, normalised by `CheckoutFragments::order_items_options()`, and the fragment passes the layout's parsed attrs, so the merchant's options survive `update_order_review`.
- **Quantity stepper:** Order Summary Items' `showStepper` option lets the shopper change or remove an item on the checkout, whichever way its `quantityDisplay` shows the quantity. WooCommerce's checkout has no endpoint that sets one item's quantity (its cart form posts the whole cart), so `Renderer\CartItemQuantity` adds the `yaycheckout_cart_item_quantity` wc-ajax action, guarded by a nonce printed on the block wrapper. `CartItemQuantity::apply()` keeps WooCommerce's cart rules: it refuses an unknown item, a quantity above `get_max_purchase_quantity()`, more than one of a sold-individually product and any change `woocommerce_update_cart_validation` vetoes (that filter's error notices become the message), removes the item at 0 and saves through `calculate_totals()`. The stepper and the remove link go through `woocommerce_cart_item_quantity` and `woocommerce_cart_item_remove_link`, so an extension that locks an item's quantity locks it here; the input has no `name` and every button is `type="button"`, so neither posts with the checkout or places the order. `assets/js/checkout-order-summary-items.js` shows a click's quantity at once and sends it 400 ms after the last click, so a run of clicks is one request; it sends the target quantity (never a step, so a repeat can't apply twice), one request at a time, keeps showing quantities not yet sent across a refresh, and holds a Place order click until they are sent. After the last request it fires `update_checkout` rather than building fragments itself, so items, totals, shipping and payment all refresh through `CheckoutFragments` as on any other change; a refused change prints its message under the items and refreshes too, so the row shows the real quantity. When the cart empties, the script sends the shopper to the cart page, since `update_order_review` answers an empty cart with WooCommerce's "session has expired" notice. The script is registered as `BlockRegistry::ORDER_SUMMARY_ITEMS_SCRIPT` and named by the block's `viewScript` for the same reason as the coupon form's: the blocks build can't declare the `wc-checkout` dependency that supplies `wc_checkout_params`, whose `wc_ajax_url` also carries a preview's token.
- **Summary collapsing:** an Order Summary whose direct children include a Summary Header or a Summary Details (the new shape) prints no `#order_review_heading`: its title is the merchant's own Heading block in the Header, so Order Summary has no Show title or Description setting. One without either prints exactly as before, and its sidebar's **Use header and details** button converts it on request, keeping the heading's text and id. `Services\OrderSummaryCollapse::state()` is the one owner of whether the summary collapses and starts open: four `render.php` files (Order Summary, Header, Details, Toggle) ask it through `of_layout( CheckoutPage::get_instance()->layout() )`, because a Summary Toggle can sit anywhere in the layout and gets no block context from the summary. It is collapsible only with `collapsible` on, a Details to hide, and a Header or a Toggle to open it; `useSummaryCollapse()` in `packages/blocks/src/order-summary/shape.ts` copies the rule for the editor. While collapsible, the Header prints an empty overlay button (`.yaycheckout-order-summary__header-button`) under its own controls, which `packages/blocks/src/order-summary/style.css` lifts above it so links and buttons keep their action, and each Toggle becomes `role="button"` with `data-yaycheckout-summary-toggle`, its links printed as text. `packages/blocks/src/order-summary/view.ts` binds both to the single `#yaycheckout-order-summary-details` and flips its `hidden`, the wrapper's `is-open` and every control's `aria-expanded` together; Details carries none of the classes `CheckoutFragments` replaces, so `update_order_review` leaves it open. The block order is the direction: a Header after Details opens them upward, so the DOM, tab and visual order always match, and the editor's Opens control reads and moves that order.
- **Block emptiness:** a Visibility "Block is empty / not empty" condition can point at any YayCheckout block in the layout whose `block.json` sets the `yaycheckoutWatchable` support (`BlockEmptiness::SUPPORT`), by its `blockId`: Shipping methods (empty when the cart needs no shipping), Payment (when the order needs no payment), Express pay (when `wc_get_pay_buttons()` prints nothing), Slot (when nothing hooked into it prints anything), Field (while WooCommerce's country locale hides it, read by `CheckoutFieldDefaults::hidden_for_country()`), Field Value (while every field it shows is empty; its view script moves the marker as the shopper types and fires `BlockEmptiness::REFRESH_EVENT`), Savings note (while savings are zero), and Coupon form, Login and Create account (when they print nothing). Each prints `data-yaycheckout-block-id` and, when empty, `data-yaycheckout-empty` on its wrapper through `BlockEmptiness::wrapper()`; a block that prints no wrapper counts as empty, and so does a deleted target. The shipping-rate, payment and savings fragments carry `data-yaycheckout-live` and their own empty marker, which the visibility script copies to the block wrapper after `updated_checkout`. A Field's wrapper carries `data-yaycheckout-locale`: on `country_to_state_changing`, after `address-i18n.js` (a dependency) has shown or hidden the row, the script marks the Field empty while its row is hidden. Coupon form, Login, Create account, Slot and Express pay keep their first-paint marker. A hidden block's required fields still validate. In the editor, a copied block keeps its original's `blockId` until the layout editor's blockId keeper (`packages/blocks/src/visibility/index.tsx`) gives every holder but the earlier one a new id.
- **Block visibility:** any block in a layout except Checkout, Steps and Step can carry `yaycheckoutVisibility`, Show when or Hide when a list of conditions all match (the open step, needs shipping, coupon applied, subtotal, logged in, and a watchable block being empty or not). `Renderer\BlockVisibility` owns the rules: on `render_block` it prints the cleaned setting on the block's first tag (`BlockVisibility::DATA_ATTR`) and adds `BlockVisibility::HIDDEN_CLASS` when the block fails with step 1 open; a setting with a block condition waits for `BlockVisibility::finalize()`, which `templates/checkout-page.php` runs over the whole rendered layout, since its target may render later. It then prints the cart and login state as a JSON element (`BlockVisibility::STATE_ID`) that `update_order_review` swaps as a fragment; `packages/blocks/src/visibility/view.ts` re-decides every conditional block on `yaycheckout:step-change`, `updated_checkout`, `country_to_state_changing` and `BlockEmptiness::REFRESH_EVENT` with `packages/blocks/src/shared/visibility-rules.ts`, the TypeScript copy of the rules, which the editor's Visibility panel and preview sidebar (`packages/blocks/src/visibility/index.tsx`) use too. A layout without the setting prints neither the element nor the script ([decision record](decisions/2026-10-13-block-visibility-in-block-markup.md)).
- **Pin to bottom:** a core Group's `yaycheckoutPinToBottom` (`PinToBottom::ALL` or `PinToBottom::MOBILE`, below 782px) fixes it to the bottom of the shopper's screen. `Renderer\PinToBottom` filters `render_block_core/group` to add `yaycheckout-pinned` (plus `yaycheckout-pinned--mobile`) and enqueue `assets/js/checkout-pin-to-bottom.js`; `checkout-base.css` does the fixing, overriding a sticky position. The class is added only on render, so the editor shows the Group in place; `pin-to-bottom.tsx` marks it with a pin on its List View row and a badge on the canvas instead. The script keeps `--yaycheckout-pinned-height`, the body's bottom padding and `scroll-padding-bottom` equal to the fixed bar's height, and on touch screens hides the bar while a field outside it has focus. The bar stays inside `form.checkout`, so a Place Order inside it still submits; a theme ancestor with a `transform` turns the fixing off. The editor's panel (`packages/blocks/src/shared/pin-to-bottom.tsx`, layout editor only) warns when another Group is pinned too.
- **Live values:** a merchant drops cart totals, cart counts and shopper fields into Paragraph and Heading text, the display text of Step, Create account and Different address, and the Place Order label (see `.claude/rules/blocks.md`), with the `yaycheckout/live-value` format (`packages/blocks/src/live-value/`). Each is a non-editable span holding `data-yaycheckout-value` (a cart key from `LiveValues::cart_values()`, or `field:<key>`), `data-fallback`, `data-prefix` and `data-suffix`; its text is only the editor's label. `Renderer\LiveValues` filters `render_block_{name}` for each of `LiveValues::BLOCKS` (copied as `LIVE_VALUE_BLOCKS` in `live-value/constants.ts`), and for Steps Progress, which prints the step titles, on a taken-over checkout only, and returns a block without the class name untouched. `fill()` prints each span's value between its prefix and suffix, or, while the value is empty (0, or a field with no text), its fallback alone, which may be `''`, and adds `is-empty`. A key the layout can't show, or a span holding tags, counts as empty and loses its key, so the script leaves it alone. Money follows `tax_display_cart`, as the Order Summary Breakdown and Order Summary Total rows do. Once a span is filled, the footer prints `#yaycheckout-live-values`, a JSON element of `LiveValues::values()`, and `LiveValues::fragments()` adds it to `update_order_review` for a layout holding a live value. `live-value/view.ts` refills cart spans from it on `updated_checkout`, and field spans from the form as the shopper types, through `fieldText()` in `shared/form-text.ts`, the reader Field Value uses. Which fields can be shown, and their values on load, come from `Renderer\ShowableFields` (copied in `shared/showable-fields.ts`), shared with Field Value. Place Order's `render.php` fills its label through `LiveValues::fill_html()` before copying the plain text into `value` and `data-value`, because WooCommerce's `checkout.js` resets the button's text to `data-value` on every payment-method click; `view.ts` then puts the label's spans back unless a gateway's `order_button_text` replaced it. In the editor, a chip whose field left the layout shows "Missing field" through a canvas style (`live-value/missing-fields.tsx`, `shared/canvas-style.ts`) and stays in the text.

## Preview links

- `POST /layouts/{id}/preview-link` returns the checkout URL with `?yaycheckout_preview=TOKEN`. `Helpers\PreviewToken` signs the layout, blog and expiry with an HMAC keyed to this purpose and blog, so the token is its own record and minting stores nothing. Anyone with the link can view it; per-link revocation isn't built.
- `Renderer\PreviewRequest` reads the token on `init` and applies its rules on `wp` at 5, before `CheckoutPage`. A preview wins over safe mode.
  - **A bad token:** on the checkout page, a token that doesn't resolve answers 410 instead of falling back to the live layout. A wc-ajax call with such a token does fall back.
  - **Hooks:** the page hooks attach only on the checkout page or a wc-ajax call. The order refusal attaches on any request carrying the argument, valid or not, and covers the classic checkout (`woocommerce_checkout_process`), not the Store API.
  - **Sample products:** an empty cart gets sample products marked with `PreviewRequest::CART_ITEM_FLAG`, saved in the viewer's WooCommerce cart. Any request without the argument strips them.

## Blocks and the embedded editor

- Blocks are dynamic: each `packages/blocks/src/<block>/` has a `block.json` and a `render.php`, and `save()` emits no markup of its own. Leaf blocks return null, and Checkout, Billing, Shipping and Order Summary save only their inner blocks (`saveNestedBlocks()` in `packages/blocks/src/shared/register-dynamic-block.tsx`). So a renamed attribute needs a default in `render.php`, not a block deprecation. `@wordpress/scripts` copies both into `assets/dist/blocks/<block>/`.
- `Blocks\BlockRegistry::register_blocks()` registers every built directory it finds, in `BlockRegistry::ORDER` (the inserter's order), so with no build there are no blocks. `allowed_blocks()` keeps `yaycheckout/*` blocks in the layout editor only, and WooCommerce's Checkout block out of it. In every other editor it turns "all blocks" into the list of blocks registered on the server, so a block registered only in JavaScript is left out. Placement rules live in each `block.json` (`parent`, `ancestor`, `supports.multiple`). Steps Progress and the Next and Previous Step buttons have no ancestor rule, so they can sit outside Checkout. Their storefront scripts fall back to the page's one `.yaycheckout-checkout` (`packages/blocks/src/shared/checkout-root.ts`), and `Renderer\CheckoutStepsProgress` reads step titles from the rendered layout's first Steps block, not from Checkout's block context. Core offers only allow-lists, so Billing, Shipping and Step keep blocks out through `allowedBlocks` built from the registry (`packages/blocks/src/shared/allowed-blocks.ts`). Containers keep core's default appender (the "+" shown while the container or a block inside it is selected), and `checkout/inserter-root.ts` points the header inserter at Checkout only while no block is selected.
- `packages/blocks/webpack.config.js` adds the `live-value/index` and `live-value/view` entries beside the `block.json` ones, which no `block.json` names. `BlockRegistry` enqueues the editor entry and its chip style only in the layout editor, so a page's Paragraph never offers the format, and registers the view entry's handles for `LiveValues::fill()` to enqueue.
- One blocks build serves both editions. It emits a script per block, and `BlockRegistry` passes `isPro`, the post type and the upgrade link as `window.yayCheckoutBlocks`. That global is printed before the Checkout block's editor script (`packages/blocks/src/shared/editor-data.ts`); the live value format's editor script, which runs after it, also reads its `liveValues`.
- `packages/blocks/src/checkout/publish-guard.ts` shows the rules of `LayoutMarkupReader::publish_error()` as a notice, and locks manual saves only while the layout is live: active (from the `yaycheckout/layout-state` store that `layout-actions.tsx` fills, so a stale editor status can't unlock it) or with an edited status of published or scheduled, as the server does; a draft saves freely. `packages/blocks/src/checkout/autosave-lock.ts` locks core's autosave (server and browser backup) on layouts, so edits reach the post only through Save or Activate. `packages/blocks/src/checkout/layout-actions.tsx` puts Save, plus Activate or Deactivate, in the editor header: Save keeps the status, Activate (held while the rules object) saves unsaved edits first, and both call the `activate` / `deactivate` routes, then reload the post record into the editor so the next save doesn't send the old status. Its Preview opens a `preview-link` in a new tab, which renders the saved markup; unsaved edits don't show. It reads `is_active` from `GET /layouts/{id}`, since `window.yayCheckoutBlocks` is printed before the post is known. `packages/blocks/src/checkout/layout-design.tsx` adds the Layout design sidebar, which edits `Layout::META_DESIGN` through the post's meta, so the header's Save stores it with the markup; it reads the schema from `window.yayCheckoutBlocks.design`, which `BlockRegistry::editor_design_data()` adds only in the block editor. It locks saving while the layout's custom CSS fails the copy of `LayoutDesign::sanitize_custom_css()`, and reprints the canvas's design style (`shared/design-css.ts`, a copy of `DesignStyles::css()`) on every change, including after the canvas iframe is rebuilt. For the picked font it asks `GET yaycheckout/v1/fonts/{slug}` for the canvas's font faces, again after every save: Google's files as a preview until the save uploads the font, then the uploaded ones.
- The admin edits a layout in core's `post.php` editor inside a modal iframe with `?yc-embed=1`. `Engine\Admin\LayoutEditorEmbed` hides the wp-admin chrome and tags the editor's REST calls with `X-YayCheckout-Embed`, and `LayoutCoreRestController::delete_item_permissions_check()` refuses delete for them: after a trash, core navigates the frame to a screen the modal can't host. Drafts save through core's REST API, so revisions come free; autosave is locked (above). On every layout edit, embedded or not, `Engine\Admin\LayoutEditorCanvas` adds a canvas style through `block_editor_settings_all` that resets the theme's content size, wide size and root padding and hides the title field, so a layout's name is changed from the layouts list's Rename action (`PUT /layouts/{id}`), not in the editor. It also hides the document bar and the Publish date row on layout screens, and the post type leaves out `page-attributes`, so there is no Parent row: the manager and the editor's Activate own a layout's status, and none has a parent. Core's Publish, Save draft, saved state, Switch to draft and Status row are hidden too, but only under `body.yaycheckout-has-layout-actions`, which `layout-actions.tsx` adds once its buttons mount, so a header it can't find leaves core's controls in place. Nothing passes messages between the frame and the SPA: the SPA refetches its layouts when the modal closes, and closing it doesn't ask about unsaved edits.

## Free and Pro

- One codebase, two zips: Free (`yaycheckout/`) without `includes/Pro/`, and Pro (`yaycheckout-pro/`) with it. Pro installs into its own folder, so a wordpress.org update for slug `yaycheckout` can't overwrite a paid install. [The decision record](decisions/2026-10-05-build-time-free-pro-split.md) says why the split is made at build time.
- PHP: `YayCheckout::boot_pro()` requires `includes/Pro/ProServiceProvider.php` when it is readable. The provider calls `Plan::mark_pro()` and attaches through hooks and filters only. `Plan::is_pro()` reports whether it booted, so it can't claim Pro while the files are missing; it describes the build, not a licence. `scripts/check-pro-boundary.sh`, run by `composer lint`, allows exactly one non-comment line naming `YayCheckout\Pro` outside `includes/Pro/`, and that line must be in `includes/YayCheckout.php` (today, in `boot_pro()`).
- SPA: `YAYCHECKOUT_PLAN` becomes `__YAYCHECKOUT_PLAN__` in `apps/admin/vite.config.ts`. With it unset, the dev server uses `pro` and a build uses `free`; `release` sets it from `--plan`. `apps/admin/src/lib/plan.ts` exposes it as `isPro`.
  - Free's upsells are teasers that ship to Free: `ProTag`, `UpgradeButton`, and the `LockedAssignment` mock in `AssignmentDrawer`. They are safe only because Free's PHP has no matching endpoint. `<ProGate>` (`apps/admin/src/components/pro/ProGate.tsx`) would blur its children the same way, but no screen uses it.
  - The template list is printed into the page for the installed plan (`templates` in `window.yayCheckoutAdmin`), and creating a layout checks `Plan::is_pro()` again. The SPA never tells the server a plan, so a dev server run with `YAYCHECKOUT_PLAN=free` on a Pro install still lists Pro's templates unlocked.
- Free allows `LayoutRepository::FREE_LIMIT` layouts and Pro is unlimited (`Plan::layout_limit()`). `LayoutRepository::insert_draft()`, behind create, duplicate and import, and `LayoutCapGuard` both ask `Plan::layout_limit_reached()`. After a downgrade from Pro, Free serves the most recently activated layout to every shopper.

## SPA and WordPress

- `Engine\Admin\Settings` enqueues the SPA only on the admin page's hook suffix, `yaycommerce_page_yaycheckout`. `Engine\Register\RegisterFacade` picks `RegisterDev` (Vite at `RegisterDev::DEV_SERVER`, port 3040) while `YAYCHECKOUT_IS_DEVELOPMENT` is true, which is the default, and `RegisterProd` (`assets/dist/admin/`) otherwise, each only if its class exists. So a release zip, which has no `RegisterDev.php`, registers neither unless the site sets the constant to false.
- `Helpers\LocalizeHelper` builds `window.yayCheckoutMeta` (REST root, nonce, site data) and `window.yayCheckoutAdmin` (settings, integrations, the template catalogue), each through a filter, and `Engine\Admin\Settings` prints them; Pro adds `store` to the admin data.
- The SPA is a hash-routed React app. `apps/admin/src/lib/api/api.ts` is the ky client, with the REST root and nonce from `yayCheckoutMeta`. Each resource has a zod schema in `apps/admin/src/lib/schema/`, its calls in `apps/admin/src/lib/api/` and its queries in `apps/admin/src/lib/queries/`; the conventions for that bridge are in [conventions.md](conventions.md).
- Production builds one entry into `assets/dist/admin/`, with React and `@wordpress/*` external. The SPA imports the blocks' shared code through the `@blocks-shared` alias.

## Compatibility scan

- `GET /compatibility` (`Controllers\CompatibilityRestController`) composes three live detections and a catalogue, and stores nothing but the catalogue transient.
- **The detections:**
  - `Helpers\StoreEnvironmentHelper` reads versions, the theme, whether the store's checkout is the block checkout, and whether safe mode is on.
  - `Helpers\GatewayCompatibilityHelper` lists enabled classic gateways, then active block payment methods with no classic gateway of the same id, flagged `block-only` unless the catalogue gives that id a status, because YayCheckout renders the classic form.
  - `Helpers\CheckoutHookScanHelper` resolves every callback on a fixed list of checkout hooks to a plugin, mu-plugin or theme by its file. Some hooks on its list, such as `woocommerce_before_checkout_form`, are ones the YayCheckout form never fires. It runs inside a REST request, so hooks added only on `wp` or `template_redirect` are invisible. A row hints that a plugin touches checkout, and a missing row doesn't prove that none does.
- **The catalogue:** `Repositories\CompatibilityCatalogueRepository` fetches the remote catalogue at `YAYCHECKOUT_COMPATIBILITY_CATALOGUE_URL` and falls back to the bundled `Support\CompatibilityCatalogue`. A failed fetch, or a document that `normalize()` rejects, caches the bundled list for `CompatibilityCatalogue::TTL_FALLBACK`. A dead endpoint therefore costs one attempt per that period, plus one per Rescan (`?refresh=true`), not one per page view. `normalize()` is the only gate the remote document passes.

## Build and release

- `./scripts/run.sh build` type-checks and builds the SPA, then the blocks. Both must build for a release: without the blocks build, a zip ships an editor with no YayCheckout blocks.
- `./scripts/run.sh release`, in order:
  1. Sets the version when one is passed or typed: the `yaycheckout.php` header, `YAYCHECKOUT_VERSION`, and `Stable tag:` in `readme.txt`.
  2. Runs the admin-shell prerelease sync, exports `YAYCHECKOUT_PLAN` and builds.
  3. Copies a fixed list into a folder named after the edition. Free deletes `includes/Pro/`; Pro renames the plugin in its header.
  4. Strips `RegisterDev.php`, `assets/dist/admin/.vite`, source maps, `.DS_Store` and `.gitkeep`.
  5. Zips into `release/`, and checks the zip for `includes/Pro/` entries against the plan.
  - It runs no lint, boundary check or tests.
- The copy list is the release: a runtime file outside it is silently absent from the zip. The list and its strip step live in `cmd_release` in `scripts/run.sh`.

## Tests

- `composer test` runs PHPUnit 9 with `phpunit.xml.dist`, or with a local gitignored `phpunit.xml` when there is one. It has one suite, `tests/Integration/`, which holds no tests today.
- `tests/bootstrap.php` loads the WordPress test library from `vendor/wp-phpunit/`, then WooCommerce (the sibling `woocommerce/` plugin) and this plugin as must-use plugins. It reinstalls WooCommerce, because the test library recreates the database on every run. `tests/wp-tests-config.php` reads the database from the environment.
- `tests/Support/` holds fakes (gateways, a layout factory). `tests/fixtures/` holds fake plugins, an mu-plugin and a theme for the hook scan. When to add a test is in [CLAUDE.md](../CLAUDE.md).
