# Architecture

**Purpose:** how YayCheckout's parts fit together: boot, the admin-shell sync, the server layers and who writes what, how a layout is stored and picked, the storefront, preview links, blocks and the embedded editor, the Free/Pro split, how the admin SPA reaches WordPress, the compatibility scan, release, and tests. Each claim names the file that decides it; read that file for the details.

**Update when:** a change moves a boundary described here: boot order or autoloading, the admin-shell sync, a layer or a writer, a stored option or post field, how the storefront picks or renders a layout, the preview rules, how blocks register or which editor offers them, the Free/Pro seam or its checks, how the SPA loads or calls WordPress, the compatibility scan, the release steps, or the test harness. A feature that stays inside an existing layer needs no update.

Commands and hard rules live in [CLAUDE.md](../CLAUDE.md). Citations give a path and a symbol, not a line number: search for the symbol. Where the code has a known gap, this doc states the behaviour as it is today.

## Boot and autoload

- `yaycheckout.php` is the entry point. Each of its constants is defined only when not already defined, so `wp-config.php` can override any of them. `YAYCHECKOUT_IS_DEVELOPMENT` is the one a site sets (see [SPA and WordPress](#spa-and-wordpress)).
- Two autoloaders run. `composer.json` classmaps only the scoped admin-shell in `vendor-prefixed/src/` and `YayCheckoutPluginAdapter.php`; `yaycheckout.php` requires `vendor/autoload.php` unconditionally, then the adapter file directly. Product classes in the `YayCheckout\` namespace go through the loader in `yaycheckout.php`, which maps them onto `includes/`, requires a file only if it exists, and uses `require_once` because a doubled backslash in a class name maps to the same file. `boot_pro()` requires `ProServiceProvider.php` by path, and Composer's `autoload-dev` maps `YayCheckout\Tests\` to `tests/`.
- That `file_exists` check lets one tree run with parts missing: Free has no `includes/Pro/`, and release zips have no `RegisterDev.php`, so code checks for those classes first (`is_readable` in `YayCheckout::boot_pro()`, `class_exists` in `RegisterFacade`) and names them only behind that check.
- Boot runs on `plugins_loaded`:
  - priority 5: admin-shell boots and registers the adapter (see [the next section](#admin-shell-sync-and-scoping));
  - priority 10: `plugin_init()` shows a notice and stops if WooCommerce is missing. Otherwise it declares HPOS compatibility (`Engine\ActDeact::before_woocommerce_init`), builds the `YayCheckout` singleton and loads translations.
- `includes/YayCheckout.php` wires everything by hand in its constructor, with no container. `boot_pro()` runs first so `Support\Plan::is_pro()` is settled before any component reads it; then REST, asset registration, the admin page, blocks and icons, the post type, the layout guards with the design-font installer, the editor embed and canvas, and the storefront renderers.
- `includes/Integrations/` holds one class per third-party plugin YayCheckout needs fixes for, each booted from `YayCheckout.php` and hooking only while that plugin is active (`Integrations\Germanized` stops Germanized's cart-item thumbnail from breaking the Items block's rows, prints its legal checkboxes in the Terms block when the layout has one, and removes its own submit button so Germanized stops hiding Place Order's). A fix for a plugin goes there, not in the renderer, its CSS included: the class adds it inline to the handle of the stylesheet it fixes (checkout-base, a block's style), only while a layout renders the checkout.
- Activation stores nothing: settings and each layout's design derive from their schemas on read. `uninstall.php` deletes layouts and options named `yaycheckout_*` only when the merchant turned on `general.delete_data_on_uninstall`; the catalogue transient, extra-field order meta, fonts uploaded into the Font Library, each user's editor-tour preferences and the other sites of a network stay behind. It runs without the autoloader, so it repeats those keys as literals.

## Admin-shell sync and scoping

- Admin-shell is a private Composer package shared by the YayCommerce plugins. It draws the shared YayCommerce admin menu and its common pages, and adds this plugin's submenu entry.
- Every plugin ships its own copy, so php-scoper rewrites the package into `vendor-prefixed/` under the `YayCheckoutScoped` namespace (`scoper.inc.php`). [The decision record](decisions/2026-10-05-admin-shell-scoped-with-php-scoper.md) says why. With several YayCommerce plugins active, the newest copy draws the shared menu.
- `YayCheckoutPluginAdapter.php` joins the two. It is a global class that implements the scoped menu-adapter interface and stays out of scoping. It names the page slug `yaycheckout` and the capability `manage_woocommerce`, and its page callback prints the SPA's mount point, `<div id="yaycheckout">`.
- The sync lives in the package's own scripts. `./scripts/run.sh dev` runs a full `composer update`, then `vendor/bin/yaycommerce-update`, which deletes `vendor-prefixed/`, updates admin-shell, requires php-scoper and thecodingmachine/safe as dev dependencies (which can rewrite `composer.json`), regenerates `scoper.inc.php` from the package's template keeping only the prefix and the adapter's name, then scopes the package and dumps the classmap.
- `./scripts/run.sh release` runs the `yaycommerce-prerelease` variant, which ends with `composer install --no-dev`. A plain `composer install` never builds `vendor-prefixed/`.

## Server layers and write ownership

- REST lives under `BaseRestController::REST_NAMESPACE` (yaycheckout/v1). `Engine\RestAPI` builds the Free controllers on `rest_api_init`; `Pro\ProServiceProvider::rest_endpoints()` builds the Pro ones, so the Free build simply has no such route. Every route, ours and core's, requires `LayoutPostType::CAPABILITY` (`manage_woocommerce`).
- Callbacks run through `BaseRestController`: `exec_read`, `exec_write_wp` for WordPress API writes, and `exec_write`, which wraps a SQL transaction, for custom tables. There are no custom tables, so nothing uses `exec_write`. WordPress writes go through the object cache, and a `ROLLBACK` would leave a persistent cache holding rolled-back data; ordering the writes so a partial failure leaves a safe state is the substitute. `LayoutRepository::archive()` deactivates before it trashes, so a refused trash leaves the layout deactivated but not archived. A thrown exception becomes a 500, its message goes back to the client, and `Helpers\Logger::exception()` logs it.
- The layers under `includes/`:
  - `Models/` are values that own their schemas and the storage keys of what they describe, and validate input against those schemas;
  - `Repositories/` hold every option call, most post and meta calls, and the invariants of their own writes;
  - `Services/` compute on data a caller already fetched, with no storage calls (`LayoutMarkupReader`, `LayoutAssignment`, `RequiredFieldOverlay`, `RequiredIndicator`, `ExtraFieldSubmission`, `Disclosure`, `OrderSummaryCollapse`; Pro's `LayoutImportReview` and `AssignmentStoreData` sit in `includes/Pro/Services/`);
  - `Controllers/` are thin, apart from `LayoutCoreRestController`, which gates core's layout routes, and `LayoutTemplateCatalogue`, which isn't a controller but the template list and its plan rule;
  - `Renderer/` hooks the storefront;
  - `Engine/` holds activation, REST and asset wiring, the admin page, the editor embed and canvas, the design-font installer (`DesignFontInstall`) and the layout guards, which enforce the repositories' rules on core's paths with their own post and meta calls.
- Writers: `LayoutRepository` writes layouts (with their `Layout::META_TEMPLATE`) and the active set; `SettingsRepository` writes `yaycheckout_settings` and its flags (`yaycheckout_settings_updated_at`, `yaycheckout_reviewed`, `yaycheckout_setup_done`); core's REST API (wp/v2) writes `post_content` and the layout's design (`Layout::META_DESIGN`) from the editor, and its logged-out view (`Layout::META_LOGGED_OUT`) when `LayoutCoreRestController::prepare_item_for_database()` moves `content` into it, kses-filtered by `LayoutRepository::filter_logged_out_content()` like every writer of that meta; `CompatibilityCatalogueRepository` caches the catalogue in a transient; `Renderer\CheckoutExtraFields` writes extra-field order meta when the order is created, and remembered extra-field values to the WooCommerce session (`CheckoutExtraFields::SESSION_VALUES`) until then; `Engine\LayoutTrashSync` deletes core's trash timestamp; `Renderer\PreviewRequest` puts a preview's sample products in the viewer's cart; `Renderer\CartItemQuantity` changes cart item quantities and removes items from the shopper's cart through its wc-ajax action; `Renderer\CheckoutLogin` signs a shopper in (`wp_signon()`) through its `wc_ajax_yaycheckout_login` action; the layout editor's tour (`packages/blocks/src/checkout/editor-tour/`) writes per-user editor preferences (core's `persisted_preferences` user meta); `FontRepository` uploads a layout's design font into core's Font Library (`wp_font_family` and `wp_font_face` posts, files in `wp_get_font_dir()`), called by `Engine\DesignFontInstall` when a design is saved (the design meta written by any writer, and every editor Save) ([why](decisions/2026-10-11-picked-fonts-installed-into-font-library.md)).
- `Models\Settings::schema()` describes every setting and `Models\LayoutDesign::schema()` every design token, each with its type and default. `Settings::from_option()` and `LayoutDesign::from_meta()` project what is stored through the schema, so a missing, stale or invalid value reads as its default and neither the SPA nor the editor meets an unknown shape; `Settings::sanitize()` checks a settings write against the same schema, and `LayoutDesign::rest_schema()` a design write.
- `POST /setup` (`Controllers\SetupRestController::complete_setup()`) validates the template before its first write, then creates the draft from it and marks setup done. Once setup is done it answers 409, so a later retry can't add a second draft; two overlapping requests both pass the check. A re-run from Settings sends `rerun`, which skips that check and always adds a draft. `LayoutTemplateCatalogue::assert_available()` decides which templates a plan may pick, and the draft is built from the picked one. `POST /mark-setup-done`, the wizard's Skip, sets the flag without a layout.

## Layouts: one post, a status and an active set

- A layout is one `yay_checkout_layout` post (`PostTypes\LayoutPostType`): `post_content` holds the block markup, and `post_status` says whether shoppers may see it. Its design is the `Layout::META_DESIGN` meta (`Models\LayoutDesign`), the only design there is: every section of `LayoutDesign::schema()` (colours, typography, inputs, checkboxes, radios, help text, buttons) with every token, plus custom CSS. Any token may be empty (`''`, or `null` for a size or radius), and an empty token prints nothing (`DesignStyles`), so the theme shows through; `design-presets.css` then gives the swatch presets, and the primary and border `checkout-base.css` reads, a theme-following fallback, and derives an empty Muted from text and background, and an empty base size, which prints `DesignStyles::DEFAULT_BASE_SIZE` (13px) ([decision record](decisions/2026-10-13-empty-base-size-prints-13px.md)). A colour is a hex colour or a theme preset's `var(--wp--preset--color--<slug>)`, and the background (a `fill`) may also be a gradient, written out to `LayoutDesign::GRADIENT_PATTERN` or a `var(--wp--preset--gradient--<slug>)`. The patterns refuse anything that could end a declaration, since tokens print unescaped, and the storefront and the editor canvas both define the preset properties. The colour tokens, less Link and Link hover (`NO_SWATCH_TOKENS`), are themselves offered to blocks as palette presets: `layout-design.tsx` adds "Design: Primary" and the rest (slug `yaycheckout-<token>`) first in every colour picker's user palette (`color.palette.custom`) through `blockEditor.useSetting.before`, and relabels that group from Custom to Checkout unless the merchant has a Global Styles palette of their own, since core groups swatches only by origin. It is added in JS, not PHP, because the post editor rebuilds its palette from the theme's global styles over REST and drops a `block_editor_settings_all` one. `assets/css/design-presets.css` defines `--wp--preset--color--yaycheckout-<token>` (each reading `--yaycheckout-design-<token>`) and its `has-*` classes, so a block that picks one follows later Design changes. A token can't name one of them (`LayoutDesign::DESIGN_PRESET_PREFIX`), since each reads a token. The design meta is registered in REST (`LayoutPostType`) with a schema built from `LayoutDesign::schema()`, so core refuses an invalid token. `LayoutRepository::duplicate()` copies it with the rules, and Pro's export file carries it; import (`LayoutImportReview::from_envelope()`) projects it through `LayoutDesign::from_meta()` instead of refusing the file, so a missing or malformed section imports as empty. [The decision record](decisions/2026-10-05-layout-is-one-post.md) says why. Publishing is a status change, the same one `activate()` and cron's `publish_future_post` make; the wire `status` is `post_status` (`Enums\LayoutStatus`). Merchants never see it: the SPA, the editor and the preview banner show Active (in the active set), Inactive or Archived ([decision record](decisions/2026-10-08-deactivate-unpublishes.md)).
- A new layout, and the setup wizard's, starts from a template in `LayoutTemplateCatalogue`: `templates/layouts/<slug>/markup.php` (`templates/layouts/pro/<slug>/` for a Pro template) gives its blocks, `design.json` its `Layout::META_DESIGN` with every section set, and `Layout::META_TEMPLATE` (`_yaycheckout_template`) records the slug. A template missing either file is listed as Coming soon (`available: false`) and refused. Each template also has a `preview.html`, the mock's page with its scripts stripped and only the CSS rules it uses, captured by `./scripts/run.sh previews` (`scripts/capture-template-previews.py`); `templates()` lists its URL as `preview_url` (`''` without one) in the catalogue `LocalizeHelper` prints, and the picker shows it in a sandboxed iframe that may not run scripts. Availability ignores it. `LayoutTemplateCatalogue::DEFAULT_SLUG` is Classic two-column: `POST /layouts` with `source: default` builds from it (the New layout modal always sends `library`), as does Reset when the layout's template is no longer available. Duplicate copies the slug and import leaves it unset. Reset (`LayoutRepository::reset()`) puts back the markup and design of the layout's template, or of the default when it has none still available, without the plan lock; the old markup stays as a revision, but the design meta has none. Classic two-column is a white header bar (logo or site title, a Cart › Checkout › Order received breadcrumb, "Secure checkout") over a constrained Group (1120px) holding the Checkout block with a two-column Columns: the form left (Express Pay, a contact row with Login, Email, the main address with Different Address and the other address, Shipping methods, Payment, Order Note, then the terms sentence, Terms & Privacy, Place Order and Return to cart), and right a sticky Group holding a white card with Order Summary (a header with its title and item count, then Items, a collapsible Coupon Form, Order Summary Breakdown and Order Summary Total, with room for the merchant's blocks around them) and the privacy and terms links. It has no footer, and the terms sentence and links print only for the pages that exist. Its look comes from block settings, not plugin CSS: the summary sticks only where the theme's settings enable sticky positioning, and on phones the columns stack form first. Its logo, links and labels are fixed at creation. Upsell & cross-sell has the same header with "Free shipping over $150" and "30-day returns" beside "Secure checkout", and the form as white cards (contact with Login and Email; the main address, holding Different Address and the other address when billing is main; Shipping methods; Payment, holding Different Address and Billing when shipping is main, then the terms sentence, Terms & Privacy and Place Order) beside a sticky summary card whose Items has the quantity stepper and which ends with a Savings note; the mock's order bump, free-shipping bar and cross-sell list have no block yet and are left out. Split express is a full-height two-column Checkout: a 520px column filled with Design: Text holding a sticky Order Summary, and the form (Express Pay over an "or" divider, Contact, the main address, Shipping methods, Payment, Different Address with the other address, Terms & Privacy and a Pay button). Multi-step wizard is a 720px column under a white header: a collapsible Order Summary card, a segments Steps Progress, then three steps (Information, Shipping, Payment) with review rows, each ending with Back and Continue or Place Order. Live receipt, Soft steps and Split express ship their own `logged-out.php`; the others use the shared one. Accordion one-page is a 640px column: a header (Back, logo or site title, Secure), "Checkout" with a text Steps Progress, four accordion step cards (Contact with Email; Delivery address with the main address, Different Address and the other address; Shipping options with methods and Order Note; Payment with the terms sentence and Terms & Privacy, kept out of the pinned bar so its text can't push Place Order off the right), and a Group pinned to the bottom holding a collapsible Order Summary that opens upward (Items, Coupon Form, Breakdown) beside a Continue that hides on the last step and a Place Order that shows only then. Minimal steps is a 440px column under a full-width bar Steps Progress: logo or site title with a text Steps Progress ("Step N of 3"), a collapsible Order Summary (item count toggle and total in the header; Items without thumbnails and Breakdown without subtotal when open), then three one-at-a-time steps (Address with Email and the main address only; Delivery with Shipping methods and a To review row; Payment with a grid of methods, the terms sentence and Terms & Privacy), Continue / Back / Pay and Secure checkout with Return to cart in a Group pinned to the bottom of the screen. Live receipt is two columns under a white header (logo or site title, Secure checkout): left a one-page form with numbered sections (Contact with Email; the main address only; Shipping methods as a grid; Payment as a box; Order Note), right a sticky monospace receipt card whose CONTACT and SHIP TO / BILL TO lines are Field Value blocks, then Items, Breakdown and Total, with coupons, the terms sentence, Terms & Privacy and Place Order below the card. Soft steps is a 560px column of filled, borderless fields: a full-width header bar that is the collapsible Order Summary's header (logo or site title, a dots Steps Progress, and a cart icon with the total that opens a grey band of Items, Coupon Form, Breakdown and Total below the bar), then three one-at-a-time steps headed by large questions (Delivery with Login, Email and the main address, plus Different Address and Shipping when billing is main; Options with a "Delivering to" review row, Shipping methods as checkmark cards and Order Note; Payment with a "Shipping" review row, a grid of methods, Different Address and Billing when shipping is main, the terms sentence and Terms & Privacy), and Continue / Back / Place Order as pill buttons after the step, not pinned. Its radios and checkboxes take their colours from the Radios and Checkboxes design. Editorial fashion is a full-height (its custom CSS) two-column Checkout with no header bar: the left column is a bag panel filled with Design: Primary (terracotta `#d9472f` in its design.json) (logo or site title with a season line, "Your bag", a large headline, Order Summary with steppers and a collapsible Coupon Form at the foot), and the right column is the form on the Design background (`#f6f1ea`) (Back to bag and Secure checkout, numbered Contact with Login and Email, the main address, Shipping methods as lines, Payment as lines holding Different Address and the other address when both exist, Order Note, the terms sentence, Terms & Privacy, Place Order with a live total, and two trust lines). Material stepper is two columns under a white header (logo or site title with "Checkout", Secure checkout): left a white card with a vertical-timeline Steps block (Contact information with Email, Phone and Login; the main address; Shipping options with methods and Order Note; Payment options with methods, Different Address and the other address when shipping is not forced to billing ("Billing address is the same as shipping" when shipping is main; "Shipping address is the same as billing" when billing is main), the terms sentence and Terms & Privacy), Continue / Back / Place Order as pill buttons inside each step, and right a sticky Order Summary card (item count, Items, Coupon Form, Breakdown and Total).
- The post type maps every capability to `manage_woocommerce` with `map_meta_cap => false`. `Controllers\LayoutCoreRestController` is its `rest_controller_class`: it requires the capability for reads too, because core answers a logged-out read of a published post, and its `prepare_item_for_database()` refuses a wp/v2 save that would leave a layout published or scheduled while `LayoutMarkupReader::publish_error()` objects. wp-admin's Quick Edit and Bulk Edit don't pass through it, so they can publish such a layout.
- `LayoutRepository::publish()` and `activate()` also refuse on `publish_error()`, and refuse an archived layout, since setting its status would restore it from the trash. `publish()` goes through `wp_publish_post()`, so a scheduled or pending layout goes live at once; `activate()` publishes first unless the layout already is, and checks the rules either way. `deactivate()` drops the layout from the active set and moves a published, pending or scheduled layout to draft; Free's `set_active()` deactivates the layout it replaces the same way. Layouts published but inactive from before this rule stay published and show as Inactive.
- The active set is the `Layout::OPTION_ACTIVE` option, an ordered list of ids, and shoppers see only layouts in it. `LayoutRepository::active()` doesn't re-check `post_status`: it relies on `LayoutActiveGuard` (below) to drop a layout that stops being visible, and an active layout that becomes scheduled keeps serving its current content. Free keeps one (`set_active()` replaces it, and `active_ids()` reads only the last id stored); Pro keeps several, most recently activated last.
- Guards keep the set honest (`includes/Engine/`):
  - `LayoutActiveGuard` refuses to trash or delete an active layout, and drops one whose status moves to anything but published or scheduled (draft, pending or private). It and `LayoutTrashSync` call `LayoutRepository::forget_active()`, which leaves the status alone, because `deactivate()` would change it again inside the transition;
  - `LayoutTrashSync` removes WordPress's trash timestamp, so an archived layout is never purged by cron.
- `LayoutRepository::archive()` deactivates before it trashes. With `EMPTY_TRASH_DAYS` set to 0, core's `wp_trash_post()` deletes instead, so archiving deletes the layout. `delete()` refuses a layout that isn't archived; core's wp/v2 `DELETE ?force=true` doesn't check.
- The layouts list's bulk actions go through `POST /layouts/bulk` (`LayoutRepository::bulk()`). It runs deactivate, archive, restore or delete on each id, and answers with the ids that ran and the ids refused, with each one's message. One refusal doesn't stop the rest. Unlike `archive()`, a bulk archive refuses an active layout instead of deactivating it, so a selection can't stop a layout serving unless the merchant chose to deactivate it.
- Layout lists are paged server-side (`Models\LayoutQuery::PER_PAGE`), and search matches titles only (`LayoutRepository::match_search_to_title()`), since `post_content` is markup. The lists show only listed statuses and the archive, so a private layout appears in neither.
- A layout may also have a logged-out view, `Layout::META_LOGGED_OUT`: the markup a guest sees when `CheckoutLogin::must_log_in()` holds (guest checkout off and no account creation at checkout), which WooCommerce answers with no form. The editor edits it as the post content: its view switch (`packages/blocks/src/checkout/layout-view.tsx`, shown while `CheckoutLogin::login_required()`, or while the logged-out view is open) reloads the embed with `LayoutEditorEmbed::QUERY_VIEW`, which the embed's apiFetch carries as `LayoutEditorEmbed::VIEW_HEADER`, so `LayoutCoreRestController` serves the meta as `content` (or, while none is saved, its template's from `LayoutTemplateCatalogue::logged_out_markup()`) and saves `content` into the meta, leaving `post_content` alone, so core's load, save and dirty state work unchanged. The switch sits in the header's toolbar, on the left. With unsaved edits it offers Save and switch, or Switch without saving, which clears the post's edits (`clearEntityRecordEdits`) so core's leave-page warning doesn't fire. The logged-out view takes no order, so the publish guard checks nothing there, and Import / Export is hidden. On the storefront `CheckoutPage::resolve()` swaps it into `$layout->content` when saved, so every reader sees one markup, and `CheckoutPage::is_logged_out_view()` makes the Checkout block print its inner blocks with no form and the Login block show regardless of the reminder setting. A preview link shows it with the same query arg. A layout created from a template starts with that template's logged-out view: its optional `templates/layouts/<slug>/logged-out.php`, or the shared `templates/layouts/logged-out.php`. It has no revisions. Duplicate, export and import copy it, the editor's Import (main view only) replaces the markup and design and leaves the logged-out view alone, and reset leaves it out.

## Storefront

- `Renderer\CheckoutPage` takes over the checkout page on `wp` when safe mode is off and a layout resolves. The order-received and order-pay endpoints stay WooCommerce's (`CheckoutPage::on_checkout_page()`). Otherwise WooCommerce is untouched, except that the opt-in `advanced.force_enqueue_checkout_scripts` setting (`Renderer\CheckoutScripts`) still loads WooCommerce's checkout scripts. A preview link resolves its own layout first (see [Preview links](#preview-links)).
- **Admin bar:** on a page `CheckoutPage::takes_over()`, `Renderer\CheckoutAdminBar` removes core's Edit Page and Edit site items, which edit neither the page nor the template shown, and gives users with `LayoutPostType::CAPABILITY` an Edit Layout item that opens the rendered layout (the previewed one on a preview link) in the SPA's editor (`Helpers\AdminUrlHelper::edit_layout()`).
- **Which layout:** `LayoutRepository::active()` gets the shopper facts that `CheckoutPage` reads (roles, logged in, `wp_is_mobile()`). Free serves its one active layout and ignores its rules; Pro hands the set to `Services\LayoutAssignment::pick()`, most recently activated first, which serves the first layout whose rules match (groups ORed, conditions ANDed; no rules matches everyone). No match leaves WooCommerce's checkout.
- Every request picks afresh, AJAX and the order submit included, with no pin, and nothing in the checkout POST says which layout rendered the form. Each `Enums\ConditionType` reads a fact that holds for the life of a form, so the shopper can't swap the layout mid-form; a fact the shopper can change, such as billing country or cart, must never become a condition. A merchant's change between render and submit (activating, editing the markup or rules, safe mode) still changes the layout the order is validated against.
- **Themeless:** `Renderer\ThemelessCheckout` decides on `setup_theme`, before core includes the theme, whether WordPress loads the bundled `templates/themeless/yaycheckout-themeless/` instead of the site's theme, so the theme's `functions.php`, assets and `theme.json` never load. The main query doesn't exist yet, so it matches the URL: the checkout page by `page_id`, `pagename` or its exact pretty path (a longer path is an endpoint such as order-received), or a wc-ajax call in `ThemelessCheckout::WC_AJAX_ACTIONS` or prefixed `yaycheckout_`. It skips admin, admin-ajax, REST, cron, the customizer, XML-RPC and WP-CLI, and swaps only when the request resolves a layout the way `CheckoutPage::resolve()` does (a preview first, then safe mode and `LayoutRepository::active()`). The swap filters the theme slug and roots the way core's customizer theme preview does, and registers the theme directory only on that request, so Appearance never lists it. The bundled `theme.json` follows Twenty Twenty-Five with a system font stack, and is what empty design tokens and `BlockGap` read. Its `index.php` prints the page's content in a bare document for a request matched here that `CheckoutPage` then doesn't take over. The `yaycheckout_themeless_checkout` filter (default true) turns it off; only a plugin or mu-plugin can hook it. Order-received and order-pay keep the site's theme. The layout editor swaps too (`ThemelessCheckout::is_layout_editor_request()`): `post.php` and `post-new.php` for a layout, and the REST calls its embed tags with `LayoutEditorEmbed::REST_HEADER`, so the canvas gets the same `theme.json` and no theme editor styles.
- **Rendering:** `template_include` at `PHP_INT_MAX` swaps in `templates/checkout-page.php`, which renders the layout before `wp_head()` (block themes print the import map there), inside the template's own document, on every theme: no theme header or footer. With themeless on (below), `wp_head()` prints the bundled theme's global styles, not the site theme's. No page title is printed. `CheckoutPage` dequeues WooCommerce's `wc-blocks-style-checkout`, `woocommerce-general`, `woocommerce-blocktheme`, `woocommerce-layout` and `woocommerce-smallscreen` and loads `Renderer\CheckoutBaseStyles`: `assets/css/design-presets.css` (the Design swatches, and the primary and border fallbacks the base reads), `assets/css/checkout-base.css`, the design font's `@font-face` rules (`Renderer\DesignFonts`, from its Font Library install; none when the theme loads the font itself), then the design. The base removes the theme's horizontal margin, padding and max-width around the layout and resets the theme.json content size, wide size and root padding inside it, so only the layout's own blocks limit its width; it also styles what several blocks or WooCommerce itself print (field rows, inputs, select2, checkboxes, notices, the blockUI spinner, buttons), and limits focus rings to keyboard focus, so a click draws no theme outline. Markup one block alone prints is styled in that block's `style.css`; Payment and Shipping methods each draw their own rows, with no shared partial. The `checkout` block prints WooCommerce's `<form name="checkout">`, and every section block sits directly inside it; nothing stops the Checkout block itself being nested. A `<form>` pair another block prints inside it, such as a currency switcher's, becomes a `<div>` pair, and an unmatched form tag is dropped (`Renderer\CheckoutNestedForms`, on first paint and on every `update_order_review` fragment): browsers drop a nested form's start tag but honour a `</form>`, which would end the checkout form there and leave the fields after it out of the order. Forms inside `<template>`, such as the Login dialog's, are left alone. The layout never passes through `the_content`, so `templates/checkout-page.php` renders it with `Renderer\LayoutShortcodes::render()`, which runs shortcodes in the Shortcode, Paragraph, Heading, Custom HTML and List item blocks only (`LayoutShortcodes::BLOCKS`), never in our blocks, which print values the shopper typed, nor in a Paragraph's live value, filled later on `render_block_core/paragraph`. It runs on `render_block` before `BlockVisibility`, skips a block holding inner blocks so nothing runs twice, and wraps a Shortcode block's output in a `div.wp-block-shortcode` that a Visibility rule can mark. `Renderer\DesignStyles` prints the rendered layout's design (`Models\LayoutDesign`) as `--yaycheckout-*` custom properties, one for each token that isn't empty plus the font size, which is 13px while its token is empty, then a page rule for the page's background, text colour and font, with a font a heading rule that makes the checkout's headings inherit it (a gradient background prints as `--yaycheckout-background-gradient` and the page's `background-image`, never as `--yaycheckout-color-background`, so the select2 dropdown, checkboxes, radios and method rows keep their solid fallback; inputs read `--yaycheckout-input-background`, then stay transparent so a field on a coloured block shows it, while the select2 dropdown, checkboxes and radios fall back to `--yaycheckout-color-background`; inputs read `--yaycheckout-input-border-color` first, then `--yaycheckout-border-color`; a focused input recolours its border and draws a flush ring in `--yaycheckout-input-focus-color`, falling back to `--yaycheckout-primary-color`, `--yaycheckout-input-focus-ring-width` wide, falling back to 1px (the Thin border focus style prints 0), and fills with `--yaycheckout-input-focus-background`, falling back to the input background; field labels, floating ones included, read `--yaycheckout-input-label-color`, then inherit (a floating label then falls back to `--yaycheckout-input-color`); the help text under every kind of field is the Muted colour (`--yaycheckout-design-muted`) and reads `--yaycheckout-help-text-size`, falling back to 0.875em; a checkbox reads `--yaycheckout-checkbox-size`, `-radius`, `-border-width` and `-checked-color`, falling back to 16px, `--yaycheckout-neutral-radius`, 1px and `--yaycheckout-primary-color`; while unticked, a checkbox reads `--yaycheckout-checkbox-border-color` and `--yaycheckout-checkbox-background`, falling back to `--yaycheckout-input-border-color` and `--yaycheckout-input-background`; a loose radio reads `--yaycheckout-radio-size`, `-border-width`, `-border-color`, `-background` and `-checked-color`, falling back to 18px, 1px, the input border, the input background and `--yaycheckout-primary-color`; the primary buttons (Place Order, Step, Coupon's filled Apply, Login's submit and WooCommerce's `.button`) read `--yaycheckout-button-background`, `-color`, `-radius`, `-font-weight` and `-text-transform`, falling back to `--yaycheckout-primary-color`, white, the neutral radius (6px on Step and Login), 600 (Step inherits its text's, Login 500) and none, and on hover `--yaycheckout-button-hover-background` and `-hover-color`, falling back to the default ones darkened by `--yaycheckout-button-hover-filter` (`brightness(0.92)`; either hover colour prints `none`); Payment and Shipping's drawn indicators read the same Radios size, border width and background, and fall back to `--yaycheckout-radio-border-color`, then the input border, and to `--yaycheckout-radio-checked-color` under their block's own Radio colours; with no Selected or Hover background of their own, Payment and Shipping Methods rows tint the selected row with the primary colour at 4% and a hovered row with the text colour at 6%, except in Cards with checkmark and Divider lines; with a Link or Link hover colour, `DesignStyles::LINK_SELECTOR` and `LINK_HOVER_SELECTOR` colour links in paragraphs, headings and Terms & Privacy that no block gives a link colour, an empty Link taking the Primary colour and an empty hover keeping the link colour, and the Login trigger and link-style disclosure toggles read the same properties, falling back to the theme's link colour), then the site-wide custom CSS (the setting `advanced.custom_css`, Settings → Advanced) and the layout's, each checked on print so a rejected one drops only itself. Tokens are values, never selectors: the base and block CSS read each property with a neutral fallback that follows the theme, so an empty token prints nothing; the font size is the one exception. `LayoutEditorCanvas` loads the same base and the edited layout's tokens into the editor canvas, without either custom CSS.
- **Fields:** the Field and Email blocks call `woocommerce_form_field()` with the value classic checkout prints, `WC()->checkout()->get_value()` (the session, or the account when logged in), so a reload keeps what the shopper typed. `Renderer\CheckoutFieldDefaults` also gives each billing or shipping row WooCommerce's `address-field` and `update_totals_on_change` classes from `woocommerce_checkout_fields`, which `checkout.js` needs to send typed address changes to `update_order_review`; layout classes such as `form-row-first` are left out. A collapsed field that holds a value prints open. Which address is the main one follows WooCommerce's `woocommerce_ship_to_destination` (`Renderer\CheckoutDifferentAddress::destination()`). When billing is main, the Different address block prints WooCommerce's own `ship_to_different_address` checkbox, and the Shipping block's `shipping_address` class lets `checkout.js` show it and send its rates fields while the box is ticked. When shipping is main, the Shipping block prints WooCommerce's box checked and hidden, and the Different address block prints "Use same address for billing" (`yaycheckout_same_billing`): `assets/js/checkout-different-address.js` hides Billing and mirrors Shipping into it, and `CheckoutDifferentAddress` copies the posted shipping address into billing and makes billing's address fields optional for that request. A layout with no Different address block always saves Shipping as typed; one with no Billing section, when shipping is main, always copies it into billing. With `billing_only`, or a cart that needs no shipping address, neither block prints and WooCommerce copies billing into shipping. Of WooCommerce's form hooks, only those around the payment methods and Place order fire by themselves; `woocommerce_before_checkout_form`, the customer-details pair, `woocommerce_checkout_billing` and `woocommerce_checkout_shipping` (account fields, order notes) fire only where a WooCommerce Hook block places them (below). Every template places a Hook block for `woocommerce_before_checkout_form` at the top of its main form column, below any header, progress bar or order summary and above the first section, and a newly inserted Checkout starts with one; plugins such as YayCurrency print their checkout notices there. It renders before the fields, so the hook still fires before they are built, and a merchant can move or delete it, for example when a field plugin's output there overrides the layout's required fields. The Create account block prints the account part of form-billing.php when WooCommerce allows registration at checkout and the visitor is a guest: the `createaccount` checkbox while guest checkout is on, then `get_checkout_fields( 'account' )` through `woocommerce_form_field()`, between `woocommerce_before_checkout_registration_form` and `woocommerce_after_checkout_registration_form`. `WC_Checkout::process_customer()` creates the account, and WooCommerce's `checkout.js` toggles the fields. A layout without the block still has WooCommerce require the account fields when guest checkout is off. The Order note block prints `order_comments` through `woocommerce_form_field()`, with Field's Show field and Required settings; `RequiredFieldOverlay::apply_order_note()`, run by `CheckoutRequiredFields`, makes WooCommerce require the note exactly when the block does, and WooCommerce saves it as the order's customer note. The Additional fields block prints the `woocommerce-additional-fields` part of form-shipping.php without its heading: `get_checkout_fields( 'order' )` between `woocommerce_before_order_notes` and `woocommerce_after_order_notes`, while `woocommerce_enable_order_notes_field` allows it. It leaves out `order_comments` when the layout has an Order note block.
- **Login:** The `yaycheckout/login` block (`Renderer\CheckoutLogin`) prints a sentence only when `woocommerce_enable_checkout_login_reminder` is `yes` and the shopper is logged out, or whenever the layout renders its logged-out view (`CheckoutPage::is_logged_out_view()`). The editor reads that option from `window.yayCheckoutLogin`. The merchant selects which phrase is the control (a span with `CheckoutLogin::TRIGGER_CLASS` in `text`, read by `CheckoutLogin::trigger_parts()`) and whether it links to `wp_login_url( checkout )` or opens a modal; a block that still has plain `text` and `linkText` uses `CheckoutLogin::split_link()`. The modal's form lives in a `<template>` and is moved to `document.body`, so it is not nested in `<form name="checkout">`. `wc_ajax_yaycheckout_login` calls `wp_signon()`; the next request, `wc_ajax_yaycheckout_login_state`, returns the logged-in layout id, account values for empty fields, and fresh `update-order-review` and `woocommerce-process_checkout` nonces. The form keeps its node: the script fills empty fields, removes the reminder, and fires `update_checkout`. It reloads the page when `form.checkout` is missing (guest checkout and registration both off: the layout's logged-out view prints with no form, or, while none is saved, the reminder prints above "You must be logged in to checkout.") or when `data-yaycheckout-layout` differs from the logged-in layout id. Six of the nine templates and every template's logged-out view include the block; a Checkout block's `defaultTemplate()` doesn't, and elsewhere the merchant adds it. The popup keeps a fixed look of its own: of the layout's design it reads only the primary colour (submit button, ticked checkbox).
- **Terms and privacy:** the `yaycheckout/terms` block (Terms & Privacy) prints WooCommerce's `checkout/terms.php`: the checkout privacy text, and the required terms checkbox when a Terms page is set, with WooCommerce's terms hooks (the before and after ones go to a WooCommerce Hook block placed for them, see below), then fires `yaycheckout_checkout_terms`, where a plugin that replaces the terms checkbox prints its own (Germanized's legal checkboxes). It prints nothing without a cart, or when WooCommerce prints no text and the action prints nothing; an extension's markup keeps the block even without text, so a placeholder its refresh fills later survives. Place Order prints only the button, the review-order submit hooks and the nonce, so the terms never share its row. Nothing adds the block for the merchant: a layout without it has no privacy text and no terms checkbox, and with a Terms page set WooCommerce refuses every order. Every template ships it.
- **Validation:** `Renderer\CheckoutRequiredFields` filters `woocommerce_checkout_fields` at 9999 through `Services\RequiredFieldOverlay::apply()`, so a billing or shipping field is required exactly when its block says so, over WooCommerce's country rules too, and any email field always is; billing and shipping fields the layout leaves out become optional. Why a field or address section is out of use for the request (the country locale hides it, billing copies shipping, the order uses no such address) is answered by `Renderer\CheckoutFieldUsage`, read by `CheckoutRequiredFields`, `CheckoutDifferentAddress` and `CheckoutExtraFields`; a new reason is added there. The filter isn't gated on the checkout page, because the checkout POST validates before `is_page()` works, so it applies to any classic checkout form on the site. `assets/js/checkout-field-requirements.js` re-applies flags and labels after WooCommerce's `address-i18n.js` resets them on a country change.
- **Remember value:** an Extra field block with `rememberValue` on carries `data-yaycheckout-remember`. On a change in one, `extra-field/view.ts` posts the checkout form to `wc_ajax_yaycheckout_remember_extra_fields`, guarded by WooCommerce's `update-order-review` nonce from `wc_checkout_params`. `CheckoutExtraFields::remember()` cleans the remembered Keys with `ExtraFieldSubmission::collect()` and replaces `SESSION_VALUES`; It also answers `woocommerce_checkout_get_value` for remembered Keys (`''` when nothing is stored, so customer meta under the same Key never leaks in), so `render.php` reads them through `CheckoutFieldDefaults::value()` like the Field block, and `RevealLink::collapsed()` prints a field holding a value open. `persist()` clears them once the order is created. Off by default, so existing layouts keep their behaviour until the merchant turns it on.
- **Coupon form:** the `coupon-form` block has no `parent`, so it can sit inside the checkout form or beside it, and it prints no `<form>` of its own because forms can't nest. WooCommerce's `checkout.js` applies a coupon only on a `form.checkout_coupon` submit, so `assets/js/checkout-coupon-form.js` posts to WooCommerce's `apply_coupon` endpoint itself, prints the response's notices under the field and fires `update_checkout`; `CheckoutFragments::drop_applied_message()` empties Woo's own success message for that request only (it posts `CheckoutFragments::COUPON_FORM_FIELD`; the cart page's `cart.js` hits the same endpoint without it), so only errors and other extensions' notices print. Applied coupons show as chips under the field, built by `CheckoutFragments::coupon_chips_html()`, which `CheckoutFragments::fragments()` refreshes on every `update_order_review` (`COUPON_CHIPS_CLASS`) without touching WooCommerce's review-order table. A chip's × is WooCommerce's `.woocommerce-remove-coupon` link, so `checkout.js` removes the coupon, and on a layout with a Coupon form, Order Summary Breakdown's coupon rows print `coupon_amount_html()` through `woocommerce_cart_totals_coupon_html`, without `[Remove]`; without one they keep Woo's row. Applied coupons are the field's value for `Disclosure::mode()`, so the form prints shown and its chips stay visible after a reload. The field carries no `input-text` or `form-row` class, so WooCommerce's inline validation leaves it alone, and the script catches Enter, which would otherwise submit the checkout. The script is registered as `BlockRegistry::COUPON_FORM_SCRIPT` and named by the block's `viewScript`, so core loads it only where the block renders; a handle, not `file:`, because the blocks build can't declare the `wc-checkout` dependency that supplies `wc_checkout_params`. Like WooCommerce's own coupon form, the block renders nothing when coupons are off or a guest must log in first. The Apply button is the `coupon-button` child block, which the form's template locks in, so its style supports (colour, typography, border, spacing, Fill or Outline) land on the `<button>`; the script still finds it by `.yaycheckout-coupon-form__apply`. The form's Button colors reach it as `--yaycheckout-coupon-button-*` custom properties on the form's wrapper, which `coupon-button/style.css` applies only while the button has no colour of its own, and `render.php` prints a default button when a saved form has no child.
- **Extra fields and fragments:** `Renderer\CheckoutExtraFields` reads the served layout's extra fields (`LayoutMarkupReader::extra_fields()`), checks them with `Services\ExtraFieldSubmission::collect()` and stores them as order meta on `woocommerce_checkout_create_order`; like the overlay, it runs on any classic checkout. An extra field may sit anywhere in the layout, Billing and Shipping included; one inside an address section the order doesn't use (Shipping when the shopper keeps one address or the cart ships nowhere, Billing when it copies Shipping) is neither validated nor stored, as WooCommerce ignores that section's own fields. A Key must match `LayoutMarkupReader::EXTRA_FIELD_KEY_PATTERN`, because a leading underscore reaches WooCommerce's internal order setters. `Renderer\CheckoutFragments` swaps the shipping-rate and payment fragments only for sections `LayoutMarkupReader::slots()` finds in the layout; a Slot block's name counts as a section. Order Summary's Items, Order Summary Breakdown, Order Summary Total and Savings note blocks are found by block name instead (`CheckoutFragments::BLOCK_FRAGMENTS`), so a Slot can't trigger them. When the layout has any of them, `update_order_review` swaps WooCommerce's `checkout/review-order.php` for the empty `templates/review-order-skipped.php`, so the table WooCommerce would build and the layout would discard never runs, and its review-order hooks fire once. Order Summary Breakdown leaves out the shipping rates, which the Shipping Methods block offers (the default layout includes one); the order total still counts them, and a layout without that block shows no rate choice. Shipping Methods prints its own rate list from `WC()->shipping()->get_packages()`, not WooCommerce's `shop_table` or `wc_cart_totals_shipping_html()`: each rate keeps WooCommerce's `shipping_method` input and runs `woocommerce_after_shipping_rate`, and the review-order shipping hooks wrap any plugin `<tr>` output in a table beside the list. `woocommerce_cart_shipping_method_full_label` receives only the method name; the price is a separate element with the same tax and zero-cost rules as `wc_cart_totals_shipping_method_label()`. Each review-order hook fires in the block that prints its content, unless a WooCommerce Hook block takes it (below): the cart-contents hooks in Items, the order-total hooks in Order Summary Breakdown (Order Summary Total prints only its row and may repeat, its fragment selector hashed from its options), the shipping hooks in Shipping Methods and the payment hooks in Payment. The Payment block's `layout` (`joined|checkmark|box|grid|cards|lines`) and Methods styles sit on the wrapper as `data-layout` and `--yaycheckout-payment-*`, so they survive `update_order_review`; the gateway list remains WooCommerce's `checkout/payment-method.php`. Items prints divs, not a table, so a row has room for a thumbnail; extensions echo table rows into the cart-contents hooks, so Items wraps any output of each in a table of its own. Items' builder receives the block's attributes, normalised by `CheckoutFragments::order_items_options()`, and the fragment passes the layout's parsed attrs, so the merchant's options survive `update_order_review`.
- **Quantity stepper:** Order Summary Items' Show as Stepper (`quantityDisplay: stepper`) lets the shopper change or remove an item on the checkout; Show as can also be Inline (`× n` beside the name) or Hidden, and `showBadge` adds a quantity badge on the thumbnail to any of them. WooCommerce's checkout has no endpoint that sets one item's quantity (its cart form posts the whole cart), so `Renderer\CartItemQuantity` adds the `yaycheckout_cart_item_quantity` wc-ajax action, guarded by a nonce printed on the block wrapper. `CartItemQuantity::apply()` keeps WooCommerce's cart rules: it refuses an unknown item, a quantity above `get_max_purchase_quantity()`, more than one of a sold-individually product and any change `woocommerce_update_cart_validation` vetoes (that filter's error notices become the message), removes the item at 0 and saves through `calculate_totals()`. The stepper and the remove link go through `woocommerce_cart_item_quantity` and `woocommerce_cart_item_remove_link`, so an extension that locks an item's quantity locks it here. With the stepper or Hidden, the row still runs `woocommerce_checkout_cart_item_quantity`, passing `''` for the inline `× n`, since extensions print item info through it (Germanized's units line). The input has no `name` and every button is `type="button"`, so neither posts with the checkout or places the order. `assets/js/checkout-order-summary-items.js` shows a click's quantity at once and sends it 400 ms after the last click, so a run of clicks is one request; it sends the target quantity (never a step, so a repeat can't apply twice), one request at a time, keeps showing quantities not yet sent across a refresh, and holds a Place order click until they are sent. After the last request it fires `update_checkout` rather than building fragments itself, so items, totals, shipping and payment all refresh through `CheckoutFragments` as on any other change; a refused change prints its message under the items and refreshes too, so the row shows the real quantity. When the cart empties, the script sends the shopper to the cart page, since `update_order_review` answers an empty cart with WooCommerce's "session has expired" notice. The script is registered as `BlockRegistry::ORDER_SUMMARY_ITEMS_SCRIPT` and named by the block's `viewScript` for the same reason as the coupon form's: the blocks build can't declare the `wc-checkout` dependency that supplies `wc_checkout_params`, whose `wc_ajax_url` also carries a preview's token.
- **Summary collapsing:** an Order Summary whose direct children include a Summary Header or a Summary Details (the new shape) prints no `#order_review_heading`: its title is the merchant's own Heading block in the Header, so Order Summary has no Label, Show title or Description setting. One without either prints exactly as before, and its sidebar's **Use header and details** button converts it on request, keeping the heading's text and id. `Services\OrderSummaryCollapse::state()` is the one owner of whether the summary collapses and starts open: four `render.php` files (Order Summary, Header, Details, Toggle) ask it through `of_layout( CheckoutPage::get_instance()->layout() )`, because a Summary Toggle can sit anywhere in the layout and gets no block context from the summary. It is collapsible only with `collapsible` on, a Details to hide, and a Header or a Toggle to open it; `useSummaryCollapse()` in `packages/blocks/src/order-summary/shape.ts` copies the rule for the editor. While collapsible, a click anywhere on the Header outside its own controls flips the summary, and each Toggle becomes `role="button"` with `data-yaycheckout-summary-toggle`, its links printed as text. A Header with a Toggle leaves the keyboard to it; one without gets `tabindex="0"` and opens on Enter or Space (it can hold links, so it takes no `role`). `packages/blocks/src/order-summary/view.ts` binds both to the single `#yaycheckout-order-summary-details` and flips its `hidden`, the wrapper's `is-open` and every Toggle's `aria-expanded` together; Details carries none of the classes `CheckoutFragments` replaces, so `update_order_review` leaves it open. The block order is the direction: a Header after Details opens them upward, so the DOM, tab and visual order always match, and the editor's Opens control reads and moves that order.
- **Block emptiness:** a Visibility "Block is empty / not empty" condition can point at any YayCheckout block in the layout whose `block.json` sets the `yaycheckoutWatchable` support (`BlockEmptiness::SUPPORT`), by its `blockId`: Shipping methods (empty when the cart needs no shipping, except for a store manager while shipping has no method; see below), Payment (when the order needs no payment), Express pay (until a gateway's script shows a button; see below), Slot (when nothing hooked into it prints anything), Field (while WooCommerce's country locale hides it, read by `CheckoutFieldDefaults::hidden_for_country()`), Field Value (while every field it shows is empty; its view script moves the marker as the shopper types and fires `BlockEmptiness::REFRESH_EVENT`), Savings note (while savings are zero), and Coupon form, Login, Create account and Terms & Privacy (when they print nothing). Each prints `data-yaycheckout-block-id` and, when empty, `data-yaycheckout-empty` on its wrapper through `BlockEmptiness::wrapper()`; a block that prints no wrapper counts as empty, and so does a deleted target. The shipping-rate, payment and savings fragments carry `data-yaycheckout-live` and their own empty marker, which the visibility script copies to the block wrapper after `updated_checkout`; so do a WooCommerce Hook block's refreshed roots. A Field's wrapper carries `data-yaycheckout-locale`: on `country_to_state_changing`, after `address-i18n.js` (a dependency) has shown or hidden the row, the script marks the Field empty while its row is hidden. Coupon form, Login, Create account, Terms & Privacy and Slot keep their first-paint marker. Express pay fires WooCommerce's classic `woocommerce_checkout_before_customer_details` and `…after_customer_details` (`Renderer\ExpressPay`), where WooCommerce prints `wc_get_pay_buttons()` and Stripe its Express Checkout container; the gateways fill those after load, so `render.php` prints nothing when the hooks print nothing and otherwise always prints the empty marker. `style.css` hides the block while the marker is set, and hides Stripe's own "OR" separator, since the layout places its own. Its view script clears the marker while an iframe or button shows and fires `BlockEmptiness::REFRESH_EVENT`. In the layout editor, `window.yayCheckoutExpressPay.hasButtons` (`ExpressPay::has_buttons()`) lets the block warn when no gateway can fill it. Stripe's classic script stands down while the checkout page holds WooCommerce's Checkout block, so `CheckoutPage` clears its `has_block` param through `wc_stripe_express_checkout_params` when the layout has an Express pay block. A hidden block's required fields still validate. In the editor, a copied block keeps its original's `blockId` until the layout editor's blockId keeper (`packages/blocks/src/visibility/index.tsx`) gives every holder but the earlier one a new id.
- **WooCommerce hooks:** the `yaycheckout/wc-hook` block (WooCommerce Hook) fires one of WooCommerce's classic-checkout actions where the merchant places it, so what plugins print there gets a block of its own instead of landing inside another block's markup. `Renderer\WcHooks::HOOKS` lists the 30 it may fire, with their group in the editor's picker, whether they pass `WC()->checkout()` as WooCommerce's templates do, and whether `update_order_review` reprints them; the editor reads them, their labels and whether anything hooks them from `window.yayCheckoutWcHooks`. Left out: the login hooks, whose inputs belong to the login dialog's own form, the per-rate `woocommerce_after_shipping_rate`, and `woocommerce_checkout_terms_and_conditions`, whose core callbacks are Terms & Privacy's content. Blocks that fire one of these hooks themselves (Express pay, Create account, Additional fields, Shipping methods, Payment, Items, Order Summary Breakdown, Place Order, Terms & Privacy) do so through `WcHooks::in_place()` or `WcHooks::without_placed()`, which stand down once the served layout has a Hook block for that hook (`WcHooks::placed()`, read with `LayoutMarkupReader::wc_hooks()`): a hook prints in one place, never twice. The Hook block fires the hook without WooCommerce's own callbacks that print what other blocks already print (`WcHooks::core_callbacks()`: the login, coupon, billing and shipping forms, notices, the review table and payment section), on a copy of the hook so the original keeps its callbacks and their order. A callback that brackets the original block's own output is anchored (`WcHooks::anchor()`): it keeps running where the hook always fired, in that block or WooCommerce's review table, and the Hook block skips it. `Integrations\Germanized` anchors its Items thumbnail switch on the cart-contents hooks this way; its payment-checkbox callback is not anchored, because it removes the checkboxes from whichever hook fires, so they follow a moved payment hook. Plugin `<tr>` output goes in a table of its own (`CheckoutFragments::wrap_extension_html()`). The cart-contents, review-order shipping and order-total hooks print a `WcHooks::CONTENT_CLASS` root even when empty, which `CheckoutFragments::fragments()` swaps on every `update_order_review`; WooCommerce's own review table, which an Order Summary without blocks prints and `update_order_review` builds, fires them with their callbacks detached (`WcHooks::mute_review_table()`, on `woocommerce_before_template_part`), so they print once and that table still refreshes. Any other Hook block prints nothing while nothing prints on its hook. A Hook block hidden by a Visibility rule still counts as placed, so its hook's output hides with it, and one for `woocommerce_checkout_before_customer_details` takes the wallet buttons from Express pay. Two Hook blocks for one hook both print it; the editor warns.
- **Setup notices:** Shipping methods and Payment print WooCommerce's own "no shipping options" and "no available payment methods" messages through `wc_print_notice()`, so they take the theme's notice markup and the checkout base styles. A user with `manage_woocommerce` also gets a hint naming the setup gap and linking to its settings: a cart that would ship on a store with no shipping method (`Helpers\CheckoutSetupHelper::shipping_needs_setup()`, where WooCommerce treats the cart as needing no shipping and shoppers see no block), or no enabled gateway (`payment_needs_setup()`). The layout editor warns on the same two gaps, from `window.yayCheckoutShippingSetup` and `window.yayCheckoutPaymentSetup` (`BlockRegistry::editor_method_setup_data()`).
- **Block visibility:** any block in a layout except Checkout, Steps and Step can carry `yaycheckoutVisibility`, Show when or Hide when a list of conditions all match (the open step, needs shipping, coupon applied, subtotal, logged in, and a watchable block being empty or not). `Renderer\BlockVisibility` owns the rules: on `render_block` it prints the cleaned setting on the block's first tag (`BlockVisibility::DATA_ATTR`) and adds `BlockVisibility::HIDDEN_CLASS` when the block fails with step 1 open; a setting with a block condition waits for `BlockVisibility::finalize()`, which `templates/checkout-page.php` runs over the whole rendered layout, since its target may render later. It then prints the cart and login state as a JSON element (`BlockVisibility::STATE_ID`) that `update_order_review` swaps as a fragment; `packages/blocks/src/visibility/view.ts` re-decides every conditional block on `yaycheckout:step-change`, `updated_checkout`, `country_to_state_changing` and `BlockEmptiness::REFRESH_EVENT` with `packages/blocks/src/shared/visibility-rules.ts`, the TypeScript copy of the rules, which the editor's Visibility panel and preview sidebar (`packages/blocks/src/visibility/index.tsx`) use too. A layout without the setting prints neither the element nor the script ([decision record](decisions/2026-10-13-block-visibility-in-block-markup.md)).
- **Pin to bottom:** a core Group's `yaycheckoutPinToBottom` (`PinToBottom::ALL` or `PinToBottom::MOBILE`, below 782px) fixes it to the bottom of the shopper's screen. `Renderer\PinToBottom` filters `render_block_core/group` to add `yaycheckout-pinned` (plus `yaycheckout-pinned--mobile`) and enqueue `assets/js/checkout-pin-to-bottom.js`; `checkout-base.css` does the fixing, overriding a sticky position. The class is added only on render, so the editor shows the Group in place; `pin-to-bottom.tsx` marks it with a pin on its List View row and a badge on the canvas instead. The script keeps `--yaycheckout-pinned-height`, the body's bottom padding and `scroll-padding-bottom` equal to the fixed bar's height, and on touch screens hides the bar while a field outside it has focus. The bar stays inside `form.checkout`, so a Place Order inside it still submits; a theme ancestor with a `transform` turns the fixing off. The editor's panel (`packages/blocks/src/shared/pin-to-bottom.tsx`, layout editor only) warns when another Group is pinned too.
- **Live values:** a merchant drops cart totals, cart counts and shopper fields into Paragraph and Heading text, the display text of Step, Create account and Different address, and the Place Order label (see `.claude/rules/blocks.md`), with the `yaycheckout/live-value` format (`packages/blocks/src/live-value/`). Each is a non-editable span holding `data-yaycheckout-value` (a cart key from `LiveValues::cart_values()`, or `field:<key>`), `data-fallback`, `data-prefix` and `data-suffix`; its text is only the editor's label. `Renderer\LiveValues` filters `render_block_{name}` for each of `LiveValues::BLOCKS` (copied as `LIVE_VALUE_BLOCKS` in `live-value/constants.ts`), and for Steps Progress, which prints the step titles, on a taken-over checkout only, and returns a block without the class name untouched. `fill()` prints each span's value between its prefix and suffix, or, while the value is empty (0, or a field with no text), its fallback alone, which may be `''`, and adds `is-empty`. A key the layout can't show, or a span holding tags, counts as empty and loses its key, so the script leaves it alone. Money follows `tax_display_cart`, as the Order Summary Breakdown and Order Summary Total rows do. Once a span is filled, the footer prints `#yaycheckout-live-values`, a JSON element of `LiveValues::values()`, and `LiveValues::fragments()` adds it to `update_order_review` for a layout holding a live value. `live-value/view.ts` refills cart spans from it on `updated_checkout`, and field spans from the form as the shopper types, through `fieldText()` in `shared/form-text.ts`, the reader Field Value uses. Which fields can be shown, and their values on load, come from `Renderer\ShowableFields` (copied in `shared/showable-fields.ts`), shared with Field Value. Place Order's `render.php` fills its label through `LiveValues::fill_html()` before copying the plain text into `value` and `data-value`, because WooCommerce's `checkout.js` resets the button's text to `data-value` on every payment-method click; `view.ts` then puts the label's spans back unless a gateway's `order_button_text` replaced it. In the editor, a chip whose field left the layout shows "Missing field" through a canvas style (`live-value/missing-fields.tsx`, `shared/canvas-style.ts`) and stays in the text.

## Preview links

- `POST /layouts/{id}/preview-link` returns the checkout URL with `?yaycheckout_preview=TOKEN`. `Helpers\PreviewToken` signs the layout, blog and expiry with an HMAC keyed to this purpose and blog, so the token is its own record and minting stores nothing. Anyone with the link can view it; per-link revocation isn't built.
- `Renderer\PreviewRequest` reads the token on `setup_theme` at 0, so `ThemelessCheckout` can see it, and applies its rules on `wp` at 5, before `CheckoutPage`. A preview wins over safe mode.
  - **A bad token:** on the checkout page, a token that doesn't resolve answers 410 instead of falling back to the live layout. A wc-ajax call with such a token does fall back.
  - **Hooks:** the page hooks attach only on the checkout page or a wc-ajax call. The order refusal attaches on any request carrying the argument, valid or not, and covers the classic checkout (`woocommerce_checkout_process`), not the Store API.
  - **Sample products:** an empty cart gets sample products marked with `PreviewRequest::CART_ITEM_FLAG`, saved in the viewer's WooCommerce cart. Any request without the argument strips them, so every preview request refills an empty cart, wc-ajax calls included: the browser's own tokenless requests, such as its favicon fetch, run alongside the preview.

## Blocks and the embedded editor

- Blocks are dynamic: each `packages/blocks/src/<block>/` has a `block.json` and a `render.php`, and `save()` emits no markup of its own. Leaf blocks return null, and the containers (Checkout, Billing, Shipping, Steps, Step, Order Summary and its Header, Details and Toggle, Coupon form) save only their inner blocks (`saveNestedBlocks()` in `packages/blocks/src/shared/register-dynamic-block.tsx`). So a renamed attribute needs a default in `render.php`, not a block deprecation. `@wordpress/scripts` copies both into `assets/dist/blocks/<block>/`. Pro blocks (today the six step blocks) live in `packages/blocks/src/pro/<block>/` and build into `assets/dist/blocks/pro/<block>/`.
- `Blocks\BlockRegistry::register_blocks()` registers every built directory it finds under `assets/dist/blocks/*/`, plus what the `yaycheckout_built_blocks` filter adds (Pro adds `assets/dist/blocks/pro/*/`), in `BlockRegistry::ORDER` (the inserter's order), so with no build there are no blocks. `allowed_blocks()` keeps `yaycheckout/*` blocks in the layout editor only, and WooCommerce's Checkout block out of it. In every other editor it turns "all blocks" into the list of blocks registered on the server, so a block registered only in JavaScript is left out. Placement rules live in each `block.json` (`parent`, `ancestor`, `supports.multiple`). Steps Progress and the Next and Previous Step buttons have no ancestor rule, so they can sit outside Checkout. Their storefront scripts fall back to the page's one `.yaycheckout-checkout` (`packages/blocks/src/shared/checkout-root.ts`), and `Renderer\LayoutSteps` reads step titles from the rendered layout's first Steps block, not from Checkout's block context. Core offers only allow-lists, so Billing, Shipping, Step, Order Summary and its Header and Details keep blocks out through `allowedBlocks` built from the registry (`packages/blocks/src/shared/allowed-blocks.ts`). Containers keep core's default appender (the "+" shown while the container or a block inside it is selected), and `checkout/inserter-root.ts` points the header inserter at Checkout only while no block is selected.
- `packages/blocks/webpack.config.js` adds the `live-value/index` and `live-value/view` entries, and their Visibility counterparts, beside the `block.json` ones, which no `block.json` names. `BlockRegistry` enqueues the editor entry and its chip style only in the layout editor, so a page's Paragraph never offers the format, and registers the view entry's handles for `LiveValues::fill()` to enqueue.
- One blocks build serves both editions. It emits a script per block, and `BlockRegistry` passes `isPro`, the post type and the upgrade link as `window.yayCheckoutBlocks`. That global is printed before the Checkout block's editor script (`packages/blocks/src/shared/editor-data.ts`); the live value format's editor script, which runs after it, also reads its `liveValues`.
- `packages/blocks/src/checkout/publish-guard.ts` shows the rules of `LayoutMarkupReader::publish_error()` as a notice, and locks manual saves only while the layout is live: active (from the `yaycheckout/layout-state` store that `layout-actions.tsx` fills, so a stale editor status can't unlock it) or with an edited status of published or scheduled, as the server does; a draft saves freely. `packages/blocks/src/checkout/autosave-lock.ts` locks core's autosave (server and browser backup) on layouts, so edits reach the post only through Save or Activate. `packages/blocks/src/checkout/layout-actions.tsx` puts Save, plus Activate or Deactivate, in the editor header: Save keeps the status, Activate (held while the rules object) saves unsaved edits first, and both call the `activate` / `deactivate` routes, then reload the post record into the editor so the next save doesn't send the old status. Its Preview opens a `preview-link` in a new tab, which renders the saved markup; unsaved edits don't show. It reads `is_active` from `GET /layouts/{id}`, since `window.yayCheckoutBlocks` is printed before the post is known. `packages/blocks/src/checkout/layout-design.tsx` adds the Layout design sidebar, which edits `Layout::META_DESIGN` through the post's meta, so the header's Save stores it with the markup; it reads the schema from `window.yayCheckoutBlocks.design`, which `BlockRegistry::editor_design_data()` adds only in the block editor. It locks saving while the layout's custom CSS fails the copy of `LayoutDesign::sanitize_custom_css()`, and reprints the canvas's design style (`shared/design-css.ts`, a copy of `DesignStyles::css()`) on every change, including after the canvas iframe is rebuilt. For the picked font it asks `GET yaycheckout/v1/fonts/{slug}` for the canvas's font faces, again after every save: Google's files as a preview until the save uploads the font, then the uploaded ones.
- A colour with states is one row with a tab per state (`StateColourItem`, `packages/blocks/src/shared/state-colour-item.tsx`), the way core shows a block's Link and its hover: in Layout design, `STATE_GROUPS` (`layout-design.tsx`) makes Link {Default, Hover} and the Inputs' Background and Border {Default, Focus}; Payment's and Shipping Methods' `COLOR_STATE_GROUPS` (`setting-controls.ts`) make Background and Border {Default, Selected, Hover} and Radio {Default, Selected}. Each state keeps its own stored key.
- `packages/blocks/src/checkout/editor-tour/` is a first-run tour of the layout editor: a spotlight and a card per step (a welcome, the canvas, the inserter, Layout design, one guided Primary colour change and where it shows on Place order, a block's Styles tab overriding it for that block, then Preview, Save and Activate). It starts by itself whenever a user opens a layout, edited or not, until that user skips, closes or finishes it, and plays again from the ⋮ menu's Editor tour (WordPress 6.6 and later). Whether a user has closed it is the `core/preferences` value `yaycheckout` / `editorTourDone`, which core keeps per user in the `persisted_preferences` user meta, so no option, route or `uninstall.php` entry owns it. In the layout editor it also turns off core's `core/edit-post` `welcomeGuide`, which would open over the tour; that preference is per user too, so the user's other post editors stop showing core's guide. The steps find core's editor areas by class names that change between WordPress releases. A step whose target hasn't shown after a short wait (Layout design unpinned, the code editor, the logged-out view with no Place order, distraction-free mode) shows its card centred with its `fallback` text, which says where the area is. Feature tours (`editor-tour/feature-tours.ts`, one entry per feature, the first being Live value) play on the same card: each starts the first time the user selects one of its blocks, never over the editor tour and only on a change of selection, and closing, skipping or finishing one adds its id to the `yaycheckout` / `featureToursSeen` preference, so it doesn't show again.
- The admin edits a layout in core's `post.php` editor inside an iframe in a full-screen modal, with `?yc-embed=1`. `Engine\Admin\LayoutEditorEmbed` hides the wp-admin chrome and tags the editor's REST calls with `X-YayCheckout-Embed`, and `LayoutCoreRestController::delete_item_permissions_check()` refuses delete for them: after a trash, core navigates the frame to a screen the modal can't host. Drafts save through core's REST API, so revisions come free; autosave is locked (above). On every layout edit, embedded or not, `Engine\Admin\LayoutEditorCanvas` adds a canvas style through `block_editor_settings_all` that resets the theme's content size, wide size and root padding and hides the title field, so a layout's name is changed from the layouts list's Rename action (`PUT /layouts/{id}`), not in the editor. It also hides the document bar and the Publish date row on layout screens, and the post type leaves out `page-attributes`, so there is no Parent row: the manager and the editor's Activate own a layout's status, and none has a parent. Core's Publish, Save draft, saved state, Switch to draft and Status row are hidden too, but only under `body.yaycheckout-has-layout-actions`, which `layout-actions.tsx` adds once its buttons mount, so a header it can't find leaves core's controls in place. Nothing passes messages between the frame and the SPA: the SPA refetches its layouts when the modal closes, and closing it doesn't ask about unsaved edits.

## Free and Pro

- One codebase, two zips: Free (`yaycheckout/`) without `includes/Pro/`, and Pro (`yaycheckout-pro/`) with it. Pro installs into its own folder, so a wordpress.org update for slug `yaycheckout` can't overwrite a paid install. With both active, the copy loaded second shows `includes/Fallback.php`'s notice and deactivates itself on `admin_init` (`yaycheckout.php`). [The decision record](decisions/2026-10-05-build-time-free-pro-split.md) says why the split is made at build time.
- PHP: `YayCheckout::boot_pro()` requires `includes/Pro/ProServiceProvider.php` when it is readable. The provider calls `Plan::mark_pro()` and attaches through hooks and filters only. `Plan::is_pro()` reports whether it booted, so it can't claim Pro while the files are missing; it describes the build, not a licence. `scripts/check-pro-boundary.sh`, run by `composer lint`, allows exactly one non-comment line naming `YayCheckout\Pro` outside `includes/Pro/` (a Free block's `render.php` counts; one under `packages/blocks/src/pro/` may name Pro), and that line must be in `includes/YayCheckout.php` (today, in `boot_pro()`).
- SPA: `YAYCHECKOUT_PLAN` becomes `__YAYCHECKOUT_PLAN__` in `apps/admin/vite.config.ts`. With it unset, the dev server uses `pro` and a build uses `free`; `release` sets it from `--plan`. `apps/admin/src/lib/plan.ts` exposes it as `isPro`.
  - Free's upsells are teasers that ship to Free: `ProBadge` (the Pro pill every locked item shows today), `ProLinkBadge` (the clickable "Pro ›" chip that opens the upgrade page, unused today), `UpgradeButton`, the `LockedAssignment` mock in `AssignmentDrawer`, the Tools page's `ExportImportCard`, and the editor's disabled Import / Export panel (`packages/blocks/src/checkout/import-export.tsx`). They are safe only because Free's PHP has no matching endpoint. `<ProGate>` (`apps/admin/src/components/pro/ProGate.tsx`) would blur its children the same way, but no screen uses it.
  - The template list is printed into the page for the installed plan (`templates` in `window.yayCheckoutAdmin`), and creating a layout checks `Plan::is_pro()` again. The SPA never tells the server a plan, so a dev server run with `YAYCHECKOUT_PLAN=free` on a Pro install still lists Pro's templates unlocked.
- Blocks: one build serves both editions, so the editor reads the plan at runtime: `window.yayCheckoutBlocks.isPro`, from `Plan::is_pro()` in `BlockRegistry::register_blocks()` (`packages/blocks/src/shared/editor-data.ts`). Unlike the SPA's `isPro`, it follows the installed plan.
  - Multi-step checkout is Pro ([decision record](decisions/2026-10-16-pro-template-previews-in-free.md)). The step blocks build into `assets/dist/blocks/pro/`, which the Free zip leaves out, and only `ProServiceProvider::built_blocks()` registers them; their block-only PHP is `Pro\Renderer\StepsProgress` and `Pro\Renderer\StepsTextStyles`. Core keeps `Renderer\LayoutSteps`, the step list, for the Visibility step rule.
  - `BlockRegistry::locked_blocks()` is the Pro blocks (`BlockRegistry::PRO_BLOCKS`) the site hasn't registered: all of them in Free, none in a built Pro. It reaches the editor as `window.yayCheckoutBlocks.lockedBlocks`, and `packages/blocks/src/checkout/locked-pro-blocks.tsx` registers each one in JavaScript only, as a locked stub: listed under its own YayCheckout Pro inserter category (`BlockRegistry::register_category()`), showing an upgrade card, taking no new inner blocks and keeping a downgraded layout's, which the merchant can move out. `BlockRegistry::allowed_blocks()` adds those names to the layout editor's list. `LayoutMarkupReader::publish_error()` refuses a live layout holding a locked block, and the editor's publish guard says so; a save that changes neither the markup nor the status, as the logged-out view's does, isn't re-checked. On the storefront an unregistered Steps or Step falls back to its saved inner blocks, `Renderer\LayoutSteps` counts no steps, and Visibility skips step rules, which the panel doesn't offer while Step is locked.
- Free and Pro both allow any number of layouts. After a downgrade from Pro, Free serves the most recently activated layout to every shopper.
- A template built from Pro blocks is marked `pro` in `LayoutTemplateCatalogue::catalogue()` and lives in `templates/layouts/pro/<slug>/`. Free lists it locked (`pro: true`, `available: false`): the picker shows its preview behind a Pro badge and an Upgrade button, `assert_available()` refuses it, and the Free zip ships only its `preview.html`. Every other template is usable in Free.

## SPA and WordPress

- `Engine\Admin\Settings` enqueues the SPA only on the admin page's hook suffix, `yaycommerce_page_yaycheckout`. `Engine\Register\RegisterFacade` picks `RegisterDev` (Vite at `RegisterDev::DEV_SERVER`, port 3040) while `YAYCHECKOUT_IS_DEVELOPMENT` is true, which is the default, and `RegisterProd` (`assets/dist/admin/`) otherwise, each only if its class exists. So a release zip, which has no `RegisterDev.php`, registers neither unless the site sets the constant to false.
- `Helpers\LocalizeHelper` builds `window.yayCheckoutMeta` (REST root, nonce, site data) and `window.yayCheckoutAdmin` (settings, integrations, the template catalogue), each through a filter, and `Engine\Admin\Settings` prints them; Pro adds `store` to the admin data.
- The SPA is a hash-routed React app. `apps/admin/src/lib/api/api.ts` is the ky client, with the REST root and nonce from `yayCheckoutMeta`. Each resource has a zod schema in `apps/admin/src/lib/schema/`, its calls in `apps/admin/src/lib/api/` and its queries in `apps/admin/src/lib/queries/`; the conventions for that bridge are in [conventions.md](conventions.md).
- Production builds one entry into `assets/dist/admin/`, with React and `@wordpress/*` external. The SPA imports the blocks' shared code through the `@blocks-shared` alias.

## Compatibility scan

- `GET /compatibility` (`Controllers\CompatibilityRestController`) composes three live detections and a catalogue, and stores nothing but the catalogue transient.
- **The detections:**
  - `Helpers\StoreEnvironmentHelper` reads versions, the theme, whether the store's checkout is the block checkout, whether safe mode is on, and how many layouts are active. The SPA's Rendering row reads the last two, and every layout mutation that can change the active set refreshes the report.
  - `Helpers\GatewayCompatibilityHelper` lists enabled classic gateways, then active block payment methods with no classic gateway of the same id, flagged `block-only` unless the catalogue gives that id a status, because YayCheckout renders the classic form.
  - `Helpers\CheckoutHookScanHelper` resolves every callback on a fixed list of checkout hooks to a plugin, mu-plugin or theme by its file. Some hooks on its list, such as `woocommerce_before_checkout_form`, fire on the YayCheckout form only where a WooCommerce Hook block places them. It runs inside a REST request, so hooks added only on `wp` or `template_redirect` are invisible. A row hints that a plugin touches checkout, and a missing row doesn't prove that none does.
- **Failures:** each detection runs on its own. One that throws is logged and comes back `null`, and the SPA shows it as "Not detected". A failed request reads the same way, with every check "Not detected", and the SPA doesn't retry it. The setup wizard doesn't scan, and the Compatibility page's Re-scan is the only manual one.
- **The catalogue:** `Repositories\CompatibilityCatalogueRepository` fetches the remote catalogue at `YAYCHECKOUT_COMPATIBILITY_CATALOGUE_URL` and falls back to the bundled `Support\CompatibilityCatalogue`. A failed fetch, or a document that `normalize()` rejects, caches the bundled list for `CompatibilityCatalogue::TTL_FALLBACK`. A dead endpoint therefore costs one attempt per that period, plus one per Compatibility page Re-scan (`?refresh=true`), not one per page view. `normalize()` is the only gate the remote document passes.

## Build and release

- `./scripts/run.sh build` type-checks and builds the SPA, then the blocks. Both must build for a release: without the blocks build, a zip ships an editor with no YayCheckout blocks.
- `./scripts/run.sh release`, in order:
  1. Sets the version when one is passed or typed: the `yaycheckout.php` header, `YAYCHECKOUT_VERSION`, and `Stable tag:` in `readme.txt`. Then sets `Tested up to:` in `readme.txt` and `WC tested up to:` in the header, from `--wp-tested=` and `--wc-tested=`, or from prompts on an interactive run.
  2. Runs the admin-shell prerelease sync, dumps a `--no-dev` authoritative autoloader, exports `YAYCHECKOUT_PLAN` and builds.
  3. Copies a fixed list into a folder named after the edition. Free deletes `includes/Pro/`, `assets/dist/blocks/pro/` and `templates/layouts/pro/`, keeping only each Pro template's `preview.html`. Free also applies `scripts/free-admin-shell.patch` to its `vendor-prefixed/` copy and deletes the shell's licensing (with the EDD updater) and Recommended Plugins page, listed in `FREE_SHELL_STRIP`. The patched copy registers election version `0.0.1`, so when another YayCommerce plugin is active its full shell runs the shared menu and keeps its Licenses page. The patch is made against the scoped shell and fails the release when the shell changes: regenerate it from the new `vendor-prefixed/`. Pro renames the plugin in its header. From Composer it copies only `composer.json` (Plugin Check wants it beside a `vendor/`), `vendor/autoload.php`, `vendor/composer/` and `vendor-prefixed/`, no packages.
  4. Strips `RegisterDev.php`, `assets/dist/admin/.vite`, source maps, `.DS_Store` and `.gitkeep`, plus each block `-rtl.css` that is identical to its LTR file. WordPress loads a block's `-rtl.css` only when the file exists.
  5. Zips into `release/` as `<slug>-<version>.zip`, checks the zip for `includes/Pro/`, `assets/dist/blocks/pro/` and `templates/layouts/pro/` entries (other than `preview.html`) against the plan, and for Free checks that no stripped shell file or reference to one remains, then dumps the autoloader again with dev maps. The packages stay `--no-dev` ([known issue](known-issues.md)).
  - It runs no lint, boundary check or tests; `composer check:boundary` runs the boundary check alone.
- The copy list is the release: a runtime file outside it is silently absent from the zip. The list and its strip step live in `cmd_release` in `scripts/run.sh`.

## Tests

- `composer test` runs PHPUnit 9 with `phpunit.xml.dist`, or with a local gitignored `phpunit.xml` when there is one. It has one suite, `tests/Integration/`, grouped by layer (`Blocks/`, `Controllers/`, `Renderer/`, `Pro/`). `Pro/` tests need `includes/Pro/`, so they run only in the dev tree.
- `tests/bootstrap.php` loads the WordPress test library from `WP_TESTS_DIR` (default `vendor/wp-phpunit/wp-phpunit`), then WooCommerce (the sibling `woocommerce/` plugin) and this plugin as must-use plugins. It reinstalls WooCommerce, because the test library recreates the database on every run. `tests/wp-tests-config.php` reads the database from the environment. It runs against the site's core files (`WP_TESTS_ABSPATH`, default four directories up) with `wptests_` tables. The site's mu-plugins don't load, but its drop-ins do.
- `tests/Support/` holds `LayoutFactory` and fake gateways. `tests/fixtures/` holds fake plugins, an mu-plugin and a theme for the hook scan. No test uses the fake gateways or the fixtures today. When to add a test is in [CLAUDE.md](../CLAUDE.md).
