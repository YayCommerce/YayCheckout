# P-1 Rules v2: layout priority, cart value and country conditions

## Goal
R-1's acceptance: *a merchant assigns a layout with the new rule conditions and the storefront serves it, including when two rules match the same cart.* On Pro, a layout's rules can test the cart subtotal and the cart quantity ("at least" / "less than" a number) and the customer's billing or shipping country ("in" / "not in" a list of WooCommerce countries), and the merchant sets which active layout wins when several match, in a Priority sheet on the Layouts page. Done means: a layout with "Cart subtotal at least 100" is served to a cart of 120 and not to a cart of 80; a layout with "Billing country in Germany" is served to a customer whose saved billing country is DE and not to one in FR; and when two active layouts both match a cart, the storefront serves the one higher in the Priority sheet, and serves the other after the merchant swaps them. Free is unchanged.

## Non-goals
- The applied coupon condition: BL-2 (it needs a coupon search route and async picker).
- Re-picking the layout when the shopper changes the country inside the form: the layout stays pinned from page load (BL-6, decided).
- Carrying priority in export files, or on Duplicate: an imported or duplicated layout takes its place when it's activated (the top).
- Warning about overlapping rules (BS-1 rejected it: undecidable cheaply, and the list order answers "which wins").
- Drag and drop in the Priority sheet: the SPA has no drag-and-drop library; up/down buttons (UX-1).
- Any change on Free: it keeps serving its one active layout and ignores rules.

## Findings
1. **The active set's order already is the priority; nothing lets the merchant set it.** `LayoutRepository::active_layouts()` reverses the stored ids (`includes/Repositories/LayoutRepository.php:78-80`), `pick()` and `outlook()` serve the first match in that order (`includes/Services/LayoutAssignment.php:30-63`), and `set_active()` appends on every activation (`LayoutRepository.php:343-357`). So priority needs only a writer for that order (T3) and no change to `pick()`, `outlook()`, `LayoutPin` or `ThemelessCheckout`.
2. **Re-activating an already-active layout would undo the merchant's order.** `activate()` calls `set_active()` unconditionally (`LayoutRepository.php:213-234`), which moves the id to the end (top priority), and the `/layouts/<id>/activate` route (`includes/Controllers/LayoutRestController.php:320`) accepts an already-active id. T3 makes Pro's `set_active()` leave an already-active id where it is.
3. **New cart facts must stay "unknown" before the cart loads.** `condition_state()` returns `null` for cart types when `CART_ITEMS` is missing (`LayoutAssignment.php:149-152`), which `outlook()` and `ThemelessCheckout` (`includes/Renderer/ThemelessCheckout.php:229-238`) rely on at `setup_theme`. The subtotal and quantity conditions do the same (T2), and join `ConditionType::CART_TYPES` (`includes/Enums/ConditionType.php:25`) so `reads_cart()` turns the pin on (`LayoutAssignment.php:70-82`, `includes/Renderer/LayoutPin.php`).
4. **Cart totals at pick time come from the session.** `CartFacts::context()` runs after `woocommerce_cart_loaded_from_session` (`includes/Renderer/CartFacts.php:17-23`); WooCommerce restores the totals there from the session (`woocommerce/includes/class-wc-cart-session.php:117`), before the checkout shortcode recalculates them. `WC_Cart::get_displayed_subtotal()` (`class-wc-cart.php:1114`) and `get_cart_contents_count()` (`:737`) read those. T2 reads them and the CartFacts test proves the subtotal is non-zero for a real cart at that point; if the session's totals turn out empty, T2 sums the items' `line_subtotal` (+ `line_subtotal_tax` when `display_prices_including_tax()`) instead, which the session also restores.
5. **A number value is new to the rules shape.** `Layout::sanitize_rule_value()` knows only keys, choices and ids (`includes/Models/Layout.php:188-208`); the SPA's wire schema already allows a number (`apps/admin/src/lib/schema/layout.schema.ts:21`), and `groupsToWire()` converts only id lists to numbers (`apps/admin/src/pages/layouts/assignment/condition-types.ts:113-121`). T1 and T5 add the number kind on both sides.
6. **`ConditionType` and `condition-types.ts` are mirrors, but not in the conventions table.** The TS file says so (`condition-types.ts:7`), `docs/knowledge/conventions.md` "Mirrored constants" doesn't list it. differs: T9 adds the row.
7. differs: `docs/knowledge/architecture.md:30` says Pro has five REST controllers; T4 adds a sixth → T9 updates it. `architecture.md:55` describes `yaycheckout_active_layout` as "oldest first"; it becomes "lowest priority first" → T9. `docs/knowledge/storefront.md:19` doesn't say which match wins → T9.
8. **Country at pick time comes from the stored customer.** WooCommerce loads `WC()->customer` from the session on `woocommerce_init`/`wp_loaded`, before `CartFacts::context()` runs; `WC_Customer::get_billing_country()` / `get_shipping_country()` hold the saved or session address, and for a new guest WooCommerce already seeds them from `wc_get_customer_default_location()` (store base or geolocation, per the "Default customer location" setting). T7 reads them, falling back to that default when empty, so the value matches the country the form opens with.
9. **Roles reach the SPA through `AssignmentStoreData::get()`** (`includes/Pro/Services/AssignmentStoreData.php:11-15`) and the role picker reads `storeData().roles` (`ConditionGroup.tsx:32`). Countries follow the same path (T7, T8), so no new route.
10. The `LayoutAssignment` class docblock says the order "stands in for a priority the merchant can't set" (`LayoutAssignment.php:10-13`) → T2 rewrites it.

## Approach
- **Conditions (Pro, storefront):** two new types in `ConditionType`: `cart_subtotal` (value kind `amount`: a number >= 0, rounded to the store's price decimals) and `cart_quantity` (value kind `count`: a whole number >= 0), with operators `at_least` (>=) and `less_than` (<). Both are in `CART_TYPES`, and each is also a context key that `CartFacts::context()` fills: the subtotal as the shopper sees it (`get_displayed_subtotal()`, so with tax when the store displays prices with tax) and the item count (`get_cart_contents_count()`). Missing from the context means unknown (`null`), as for products. Rules keep their shape; export/import/duplicate pass through `Layout::sanitize_rules()` unchanged.
- **Country conditions (Pro, storefront):** `billing_country` and `shipping_country` in `ConditionType`, value kind `countries` (a list of ISO codes, each a key of `WC()->countries->get_countries()`, at most 300), operators `in` / `not_in` (the existing `LIST_OPERATORS`). A new `ConditionType::PINNED_TYPES` = `CART_TYPES` + the two country types, and `reads_cart()` tests `PINNED_TYPES`, so a country rule turns the pin on: the country is read once at page load and a mid-form country change on `update_order_review` doesn't swap the layout (BL-6). A new `includes/Renderer/CustomerFacts.php` fills both context keys when `WC()->customer` is a loaded `WC_Customer` (after `woocommerce_cart_loaded_from_session`, like `CartFacts`); shipping falls back to billing, both fall back to `wc_get_customer_default_location()['country']`; an empty result leaves the key out. Missing from the context means unknown (`null`, outlook `maybe`), as for the cart facts. `LayoutPin` merges `CustomerFacts::context()` beside `CartFacts::context()`; `ThemelessCheckout` runs at `setup_theme`, before the session loads, so it gets neither and decides from the outlook (`maybe`) and the pin hint, as for cart rules.
- **Priority (Pro, storage):** the stored order of `yaycheckout_active_layout`, lowest first, as today. `LayoutRepository::priority()` returns the active layouts top first (the existing `active_layouts()`), and `set_priority( int[] $ids )` takes ids top first, refuses any list that isn't exactly the current active set (a stale screen), and stores it reversed through `store_ids()`. Pro's `set_active()` appends only ids that aren't already active. Free keeps `array_slice( $ids, -1 )`, the top of the list. Hard rule 4: only `LayoutRepository` writes the option.
- **REST (Pro):** new `includes/Pro/Controllers/LayoutPriorityRestController.php`, extending `BaseRestController` with its `manage_woocommerce` check (hard rule 6): `GET /layouts/priority` → `{ layouts: summary[] }` top first; `PUT /layouts/priority` body `{ ids: int[] }` → the same reply, 409 via `error_conflict()` for a stale list, 400 for a malformed one. Registered in `ProServiceProvider` beside the other Pro controllers (hard rule 1: nothing outside `includes/Pro/` names it).
- **Admin (Pro):** UX-1. The condition type menu gains "Cart subtotal" and "Cart quantity" with a number input; chips read "Cart subtotal at least 100". "Billing country" and "Shipping country" use a searchable multi-select over `storeData().countries` (from `AssignmentStoreData`), with UX-1's help line that the country is read when checkout opens. A "Priority" button in the Layouts toolbar (behind `isPro &&`, shown when two or more layouts are active, hard rule 2) opens a sheet listing the active layouts top first with move up/down and Save priority.
- **Compatibility:** classic checkout only (the plugin replaces it); HPOS untouched (no order data). The pin keeps a form's layout while the merchant reorders; the next checkout page load uses the new order. No shipped users, so no migration.
- **Mirrors (hard rule 7):** `ConditionType` ↔ `condition-types.ts` change in the same commit (T1/T7 and T5/T8 are separate commits, but T5's types only exist once T1 accepts them on save; T1 alone ships types the SPA can't yet pick, which is harmless).

## Decided
- Country conditions added on the user's call (R-1 autopilot sheet), read from `WC()->customer` with the default-location fallback and pinned at page load (BL-6).
- `PINNED_TYPES` widens `reads_cart()` instead of putting country in `CART_TYPES`, so the cart-items unknown check stays about the cart.
- Countries reach the SPA through `AssignmentStoreData`, like roles: no new REST route.
- T7: `ThemelessCheckout` is unchanged: it never merged `CartFacts::context()` and runs before the customer loads, where `CustomerFacts::context()` is empty; a country rule makes `depends_on_cart()` true, so it decides from the outlook and the pin hint, which is the behaviour the plan wants.
- T7: `AssignmentStoreData` decodes the HTML entities WooCommerce writes in some country names (`&#197;land Islands`), since React prints them as typed.
- T3: `set_priority()` compares against the active layouts that still exist (`priority()`), so an id left in the option for a deleted post is dropped on the next save instead of blocking it forever; it also refuses on Free.
- T8: the country operators are `in` / `not_in` labelled "in" / "not in" (their own list), not the role picker's "in list" / "not in list", so the chip reads "Billing country in Germany" as UX-1 asks. The pickers' accessible names needed an optional `aria-label` on `OptionsMultiSelect` and `MultiSelectTrigger`.
- T5: the number value is `NumericFormat` over `Input`, not `NumberInputRoot`: that component always holds a number (an empty field reads as its default 0), so an empty value could not keep Save rules disabled as UX-1 asks. `AssignmentChips.tsx` needed no change: `valueText()` already prints a number.

## Risks
- **The priority write overwrites a concurrent activation.** Mitigated by refusing a list that isn't exactly the current active set (409, the sheet reloads). Rollback: revert T3/T4; the stored order stays valid for the old code, which reads the same option the same way.
- **Stale totals at pick time.** If the session carries no totals for a cart (Finding 4), `get_displayed_subtotal()` would read 0 and a "less than" rule would match wrongly. The CartFacts test pins it; the fallback is summing item line subtotals.
- **Multi-currency plugins.** A currency switcher that converts cart prices makes the subtotal the shopper's currency while the threshold is a plain number the merchant typed. Accepted for v2 (the comparison uses whatever the cart reports); a filter on the CartFacts subtotal can follow if a store asks.
- **The pinned layout ignores a mid-form cart change.** By design (as for product conditions): the next checkout page load re-picks. A shopper who crosses a threshold in the form keeps the layout they started with.
- **The country the layout used differs from the one the shopper types.** Decided (BL-6): pinned at page load; a mid-form country change does not swap the layout. UX-1's help line tells the merchant. Re-picking mid-form is out of scope.
- **Geolocation and page caching.** With "Geolocate (with page caching support)" the default country for a new guest can come from a cached page's guess; the condition then uses whatever `WC()->customer` reports. Accepted, as WooCommerce's own tax/shipping defaults behave the same.
- Rollback for the whole plan: revert the PR; stored rules with the new types then show as "not supported by this version" in the drawer and never match (`LayoutAssignment::condition_state()` default branch, `ConditionGroup.tsx` unknown-type row), so nothing breaks.
- Decided (autopilot sheet): R-1 Rules v2 ships cart subtotal, cart quantity and billing/shipping country in 1.1.0 (the user chose country over the recommendation); country is pinned at page load (BL-6); coupon stays deferred under BL-2.
